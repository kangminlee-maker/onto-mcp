2. Review Execution Flow

review는 하나의 호출을 interpretation/binding으로 고정한 뒤, lens를 분리된 context에서 실행하고, 모든 issue에 대한 stance와 이견을 보존한 상태로 controlled deliberation을 수행합니다. 명시적 단일 lens selection도 지원하며, 이 경우 cross-lens disagreement는 적용되지 않는 bounded single-lens evidence로 기록됩니다.

1. MCP Callonto_review receives target, intent, optional domain and lens controls.
2. Core APIreview-api.ts captures runtime facts and returns structured refs plus llmPresentation prompts.
3. Invocationinterpretation and binding are materialized as runtime-owned artifacts.
4. Preparationpre-dispatch gates, execution plan, review context manifest, packet refs, and packet hashes are written.
5. Isolated Lensselected lens set runs through worker seats only after manifest and packet guards pass.
6. Issue Closurefindings are grouped into root-cause issue clusters and stance matrices.
7. Deliberationcontested positions are revisited by participating lens contexts under teamlead control.
8. Synthesizesynthesis consumes lens outputs and deliberation result, writes a comprehensive final result, and preserves compact Boundary Notes for non-material evidence gaps.
9. RecordReviewRecord, manifest, final output, and MCP result overview are produced.

2A. Reconstruct Seeding And Maturation Flow

reconstruct는 source material에서 목적 authority를 먼저 확보한 뒤 seed를 만들고, seed를 바로 action-ready로 주장하지 않습니다. 현재 활성 구현은 seeding S1-S4와 maturation M1-M4 projection이며, final re-question과 proof-boundary는 runtime authority로 기록됩니다.

1. Control & Verify Registryreconstruct-run-control.yaml atomically admits the session owner or a promoted resume attempt with matching provenance, then registry-verification-evidence.yaml proves the current active registry subjects before runtime profiles target material or consumes semantic artifacts.
2. PurposeLLM authors source-purpose-candidates.yaml; runtime validates evidence, P1-P5 strength, mixed lineage, and confirmation need.
3. Confirmpurpose-confirmation-validation.yaml gates inferred or limitation-backed purpose before seed readiness projection.
4. Seedcandidate inventory, disposition, ontology-seed.yaml, material-admission validation, claim realization, seed confirmation, and competency checks run against validated purpose authority.
5. Handoffpre-handoff manifest and handoff validation decide seed iteration readiness without claiming action-ready ontology.
6. Baselinematuration-baseline.yaml projects purpose elements across static, kinetic, dynamic surfaces and maturity dimensions from the validated seeding record ref/hash.
7. Matrixactionability-matrix.yaml marks rows closed, limitation-backed, or frontier-required from validated baseline evidence.
8. Frontiermaturation-question-frontier.yaml exposes material unanswered rows as concrete next questions.
9. Supportmaturation-closure-frontier.yaml, source-observation-lineage-index.yaml, source-observation-lineage-index-validation.yaml, maturation-authority-response.yaml, and answer-support-ledger.yaml separate next evidence requests from batch-scoped validated lineage and consumption-scoped source-safety-validated answer support. Direct-call answer support receives a bounded closure-prioritized prompt-visible source-observation catalog ordered by global closure hint, all requested source, all member source, then all cross-material source refs, and fails closed when prioritized evidence would overflow the catalog.
10. Expandmaturation-answer-claims.yaml and ontology-expansion.yaml project supported answers as overlay changes without rewriting ontology-seed.yaml.
11. Continuematuration-source-delta.yaml records source impact, maturation-convergence-ledger.yaml records final re-question status, and maturation-continuation-decision.yaml projects continue, ask user, blocked, actionable limited, or actionable ready from validated state.
12. PublishPre-publication claim-projection.yaml is derived from runtime authorities and the immutable run-control checkpoint first; final-output.md then cites claim authority refs and is validated as a consumer.

10. Boundary Decisions

Canonical public path

onto mcp exposes MCP tools. Review-specific npm scripts have been removed from the public package surface; internal harnesses call TypeScript entrypoints directly.

Deliberation transport

SendMessageA2A is treated as one host transport idea. The product requirement is transport-neutral: different context-isolated lens units must revisit contested claims under teamlead-controlled deliberation.

Presentation ownership

Runtime owns bounded facts and artifact truth. Host LLM owns user-facing explanation through llmPresentation prompt/input pairs, so MCP clients do not depend on CLI stdout formatting.
