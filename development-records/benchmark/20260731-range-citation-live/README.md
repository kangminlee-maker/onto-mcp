# 구간 인용 — 라이브 실증 (2026-07-31)

`npx tsx scripts/observation-citation-live.mts`

이 트랙(구간 단위 배달·인용)의 **목적**을 라이브로 태운 arm이다. 앞선 두 arm은 전송을 증명했다 —
실 워커가 페이지를 받고 재조정이 도달을 확인한다. 저작 파이프라인은 타지 않았으므로 "관찰을 일부만
읽고 그 구간만 인용해도 성립한다"는 결정론으로만 증명돼 있었다. 이 런이 그것을 실물로 돌린다:

```
실 코퍼스 → 실 façade → 실 codex 워커가 무엇을 인용할지 스스로 고름 → 실 인용 게이트
```

| 파일 | 무엇 |
|---|---|
| `verdict.json` | 판정 수치 — 피검 관찰, 예산, 방출/배달/인용 구간, attestation |
| `delivery.json` | 재조정 레코드 — 무엇이 워커 문맥에 실제로 도달했는가 |
| `answer-support-ledger.json` | 저작된 원장 — 게이트를 통과한 evidence ref |

## 무엇이 증명됐나

| | 값 |
|---|---|
| 피검 관찰 | `obs_020ed9af3779fd3d`, **82,717자** |
| 예산 | 38,000 **렌더 결과** chars (S4′) |
| 방출·배달 | 1페이지, 배달 구간 `[0, 16812)` |
| **인용** | **16,812 / 82,717자 = 20.3%** — 구간 하나 |
| attestation | 1/1 `verbatim_delivered`, 최대 **18,186 page chars** |

- **부분 인용이 라이브로 관측됐다.** 실 워커가 레코드를 통째로 인용하지 않았고, 런타임은 인용한
  부분을 수용했다. 구 관찰 단위 규칙에서는 표현조차 불가능한 형태다
- **S4′의 라이브 조건이 닫혔다.** 천장 크기 페이지가 워커 전사본에서 **정본 그대로** 발견됐다 —
  결정론으로는 만들 수 없는 주장이고, 2026-07-31의 봉투 사이징 결함이 깨뜨렸던 바로 그 주장이다
- **음성 arm이 같은 런의 실 데이터 위에서 돌았다**: `[0,16812)`은 인용 가능하고 `[0,16813)` —
  한 글자 더 — 는 거부된다. 대조 쌍이라 "전부 수용"하는 규칙은 통과하지 못한다

## 게이트한 것과 보고만 한 것

워커가 구간 하나를 인용할지 다섯을 인용할지는 **모델의 판단**이다. 거기에 게이트를 걸면 프로브가
런타임이 아니라 모델에 대해 플래키해진다 — 이 트랙이 네 번 밟은 함정이다. 그래서 게이트는
런타임 사실에만 걸린다(ref가 range identity를 갖는가 · 방출 표에 해소되는가 · 배달 커버리지 안인가 ·
천장 근처 페이지가 정본으로 도달했는가). 부분성 여부는 **보고**한다.

## 이 arm이 찾은 결함 셋

원래 목적보다 부수 발견이 컸다. 셋 다 기존 결정론 테스트로는 도달 불가였다 — 그 테스트들은 모델을
스텁하고 **항상 무언가를 인용**하므로, "실제 모델이 이 지시를 따를 수 있는가"를 묻지 않는다.

| | 무엇 | 처분 |
|---|---|---|
| **D1** | 시스템 프롬프트가 JSON 모양을 `evidence_observation_ids`로 선언하는데 풀 모드 런타임은 `evidence_range_ids`를 읽는다. 실 워커는 이 모순을 **빈 클러스터**로 해소했다(출력 6토큰) | 수정 — 모드-aware 두 투영 |
| **D2** | 배달 basis에 빈 인용 가드가 없어 range를 하나도 안 댄 클러스터가 **증거 0개로 통과**한다(실측 `CLUSTERS=1 REFS=[]`) | 수정 — 거부를 basis 분기 앞으로 |
| **D3** | `independence_basis`를 모든 모드에서 비어있지 않게 요구하는데 프롬프트는 필수라고 말하지 않는다. `direct_authority`에는 기술할 독립성이 없다 | 수정 — 프롬프트가 요구사항을 말한다 |

**D1의 인과는 단일 변수로 확인했다**: 모델·effort를 고정하고 프롬프트만 교체하자 출력이 6 → 140토큰이
되고 인용이 나타났다. D3는 `low`·`medium` 두 effort에서 동일 재현이라 좌석 문제가 아니었다.

## 교훈

- **계약을 두 곳에 적으면 모델이 그 모순을 조용히 해소한다.** D1에서 모델은 틀리지 않았다 — 서로
  다른 두 지시를 받고 가장 안전한 답(아무것도 인용하지 않음)을 골랐다. 형식 오류가 아니라 **빈 성공**
  이라 게이트가 잡을 것도 없었다
- **실패 지점이 곧 증거다.** 게이트 통과 여부를 추론하지 않고 실패 메시지의 출처로 판정했다 —
  게이트가 거부했다면 게이트의 문장이 나왔어야 했다
- **프로브 자신의 설정이 결함이 사는 곳이다.** 첫 시도는 `provider_identity`를 `provider` 대신 써서
  라우트 가드에 막혔다(쿼터 0 소모). 그래서 디스패치 직전까지만 도는 무료 dry-run을 넣었고,
  그 dry-run이 **관측할 수 없는 것**(디스패처 내부의 라우트 해석)도 스크립트에 명기했다
