# Synthesize

## Consensus
- issue-001 (high): 임상의가 신뢰해야 하는 Report.result_status가 Result.status 정정 이후 야간 배치 전까지 stale 상태로 남을 수 있어, 보고 상태 권위 계약을 약화시키는 high/material 이슈입니다.
  - root cause: 보고 상태의 신뢰 가치와 운영 편의성인 야간 배치 동기화가 같은 계약 안에서 조정 없이 병존합니다.
  - materiality: 검토 목적은 EMR/LIS 통합 설계의 개념 권위 문서로서 결과·보고 상태의 권위를 정렬하는 것입니다. 그런데 clinician-facing 상태를 신뢰 가능한 권위값으로 선언하면서 corrected 반영 지연을 정상 계약으로 허용하면, 통합 구현자는 stale 보고 상태를 허용 가능한 상태로 받아들일 수 있고 임상의가 보는 상태의 신뢰 의미가 약해집니다.
  - action: Report.result_status의 권위 원천을 Result.status에 종속된 파생값으로 명확히 낮추거나, corrected 전이를 Report.result_status에 동기적으로 반영해야 하는 불변식으로 올려야 합니다. 배치 처리가 반드시 필요하다면 배치 전 구간의 Report를 stale 또는 pending_amendment 같은 명시 상태로 표시하고, 그 동안 임상의가 신뢰할 수 있는 범위와 제한을 문서화해야 합니다.
- issue-004 (high): 결과 상태와 보고 상태가 중복 현재값으로 존재하지만 단일 권위, 상태 이벤트, 버전 이력이 없어 EMR/LIS 상태 계약이 닫히지 않습니다. 특히 Result.status가 corrected로 바뀐 뒤 야간 배치 전까지 Report.result_status가 finalized로 남는 구간과, 과거 특정 시점에 임상의가 실제로 본 상태를 재구성해야 하는 구간을 설명할 수 없습니다.
  - root cause: Result.status와 Report.result_status가 현재값 속성으로 중복 저장되지만 단일 source-of-truth, 상태 이벤트, 버전 이력 개념이 없다.
  - materiality: 이 온톨로지는 EMR/LIS 연동 설계의 개념 권위 문서로서 결과 상태와 보고 상태의 precedence 및 운영 위험을 닫아야 합니다. 그런데 임상의가 신뢰하는 Report.result_status와 LIS가 기록하는 Result.status가 동시에 상태 정보를 보유하고, corrected 반영은 야간 배치에 의존하므로 지연 구간의 신뢰 기준, 정정 보고 추적성, 과거 보고 상태 재현 기준이 필요합니다. 이 기준이 없으면 핵심 운영 계약이 불완전해집니다.
  - action: 상태 권위 및 이벤트/버전 개념을 추가해야 합니다. ResultStatusAuthority 또는 ResultStatusEvent/ReportReleaseEvent 같은 개념을 두고, 상태 변화에 effective_at, recorded_at, source_system, supersedes/replaces, released_version을 연결하며, Report가 표시하는 상태가 어떤 Result 상태 이벤트에서 파생되었는지 명시해야 합니다. 이 작업은 중복 상태 필드의 권위와 mapping을 먼저 닫은 뒤 지연 동기화, 정정 보고, 과거 노출 상태 재구성 규칙을 그 위에 세워야 합니다.
- issue-005 (high): CriticalValue 통보는 단순 완료 여부가 아니라 감사 가능한 운영 행위로 모델링되어야 합니다. 현재처럼 notified boolean과 외부 전화 기록 대장에 의존하면 CriticalValueNotification 또는 NotificationAttempt 같은 이벤트 개념이 없어 통보 책임, 지연, 누락, 재시도, 수신 확인을 온톨로지 자체에서 표현할 수 없습니다.
  - root cause: 통보를 독립적인 감사 가능한 행위/이벤트가 아니라 CriticalValue의 완료 여부 속성으로 축소했다.
  - materiality: 이 온톨로지는 위험 결과의 즉시 통보와 EMR/LIS 운영 책임을 설명하는 개념 권위 문서 역할을 해야 합니다. critical value가 발생했을 때 누가 누구에게 언제 어떤 채널로 통보했는지, 실패나 지연이 있었는지, 수신 확인이 되었는지를 공통 개념으로 표현하지 못하면 안전 관련 운영 책임과 감사 추적이 모델 밖으로 빠집니다. 따라서 notified boolean만으로는 실제 통보 이행을 검증할 수 없어 목적을 materially 약화합니다.
  - action: CriticalValueNotification 또는 NotificationAttempt 엔티티를 추가하고 critical_value/result_ref, notified_by, recipient, notified_at, channel, acknowledgement_at, outcome, failure_reason, retry_of를 모델링해야 합니다. 이 이벤트를 CriticalValue 또는 Result와 관계로 연결하고, 기존 notified boolean은 이벤트 기록에서 파생되는 값으로 낮추는 것이 안전합니다. 이렇게 해야 통보 책임, 지연, 누락, 실패, 재시도, 수신 확인을 EMR/LIS 통합 권위 모델 안에서 감사 가능한 형태로 다룰 수 있습니다.
- issue-011 (high): Order.completed가 현재 Result.status 값에 의존하는데, 이후 Result가 corrected로 바뀔 수 있어 completed 상태의 의미가 lifecycle 전반에서 불안정해집니다. 이 이슈는 corrected 결과 이후 Order가 계속 completed인지, reopened/amended되어야 하는지, 또는 최초 finalization만 의미하는지 정의하지 못하는 고심각도 상태 계약 모순입니다.
  - root cause: Order completion이 mutable current Result.status에 대한 술어로 정의되었지만 correction 이후 Order 전이나 immutable completion snapshot이 없다.
  - materiality: 이 온톨로지는 EMR/LIS 통합 상태 계약의 개념적 권위로 쓰이므로 Order.completed는 downstream 시스템이 신뢰할 수 있는 완료 상태여야 합니다. 그러나 completed가 모든 현재 Result가 final이라는 뜻인지, 한 번 finalization이 발생했다는 이력 상태인지 구분되지 않으면 corrected lab result 이후 통합 시스템마다 서로 다른 해석을 하게 되어 완료 상태의 계약성이 약해집니다.
  - action: 완료 의미를 immutable event/snapshot 기준으로 재정의하거나, correction 이후 completed Order가 amended 또는 reopened 같은 명시 상태로 전이되는 규칙을 추가해야 합니다. completed를 correction 이후에도 유지하려는 의도라면 completed는 최초 finalization을 뜻한다고 밝히고, 현재 결과 수정 상태나 amendment 상태는 별도 속성 또는 lifecycle 축으로 분리해야 합니다.
- issue-013 (high): Result.status와 Report.result_status가 같은 상태 정보를 다루는 것처럼 설명되지만, 서로 다른 enum과 권위 주장을 갖고 있어 EMR/LIS 통합에서 상태 의미의 단일한 해석 기준이 깨집니다.
  - root cause: Result와 Report 상태가 별도 enum으로 중복 모델링되었지만 canonical status authority, 완전한 매핑, 지연 표시 상태가 정의되지 않았다.
  - materiality: 이 온톨로지는 결과 및 보고 상태를 EMR/LIS 통합에서 확장 가능하고 일관되게 해석하게 하는 개념 권위 문서여야 합니다. 그런데 LIS가 Result.status를, EMR이나 임상의 화면이 Report.result_status를 기준으로 삼으면 preliminary/prelim, final/finalized, corrected/amended 같은 값 차이가 같은 검사 결과의 신뢰도와 후속 조치를 다르게 해석하게 만들 수 있습니다. 특히 corrected와 amended는 결과 정정과 보고서 개정이라는 다른 사건일 수 있어 단순 동의어로 두기 어렵고, 새 상태가 추가될 때 기존 데이터 해석의 연속성도 흔들립니다.
  - action: 원천 상태와 표시 상태의 권위를 먼저 정해야 합니다. 안전한 수습 방향은 canonical ResultStatus를 하나 두고 Report가 이를 참조하거나 투영하게 하거나, ResultStatus와 ReportStatus를 의도적으로 분리하되 각 값의 의미, 버전 있는 매핑, 전이 규칙, 동기화 지연 상태를 명시하는 것입니다. 이 순서가 필요한 이유는 authority와 매핑 기준이 먼저 확정되어야 corrected/amended 같은 현재 값과 향후 추가 상태의 해석을 안정적으로 연결할 수 있기 때문입니다.
- issue-003 (medium): TAT 산출 기준을 대시보드 팀의 자체 계산식으로 남기면 통합 온톨로지가 공통 운영 지표의 권위를 제공하지 못합니다. turnaround_time은 온톨로지 안에서 권위 있는 파생 속성 또는 projection으로 닫혀야 합니다.
  - root cause: 권위 문서가 파생 지표의 canonical authority를 닫지 않고 downstream 팀의 자체 계산식을 허용합니다.
  - materiality: EMR/LIS 통합 권위 문서의 핵심 가치는 시스템과 팀 사이의 해석 차이를 줄이는 데 있습니다. TAT는 운영 성과와 우선순위 판단에 쓰일 수 있는 파생 지표이므로, 계산식과 예외 기준이 문서 밖의 대시보드 로직에 남아 있으면 같은 검사 흐름도 서로 다른 TAT 값으로 해석될 수 있습니다.
  - action: turnaround_time을 온톨로지의 파생 속성 또는 명시적 projection으로 정의하고, source fields, timezone, missing timestamp, corrected/amended report 처리 기준을 함께 포함해야 합니다. 대시보드 계산식은 별도 권위가 아니라 이 canonical rule의 구현체로 표현되어야 하며, 그래야 지표 재현성과 해석 분쟁 해결 책임이 통합 권위 문서에 남습니다.

  - action: Specimen에 stored, retention_expired, disposal_pending, disposed 같은 보관·폐기 lifecycle 상태를 추가하거나, SpecimenRetention 및 SpecimenDisposalEvent 같은 엔티티와 관계를 도입해야 합니다. 부서별 내규는 상태 개념을 대체하지 말고 retention_policy_ref, storage_location, disposed_at, disposed_by 같은 속성이나 참조로 연결해 공통 상태와 로컬 정책을 분리해야 합니다.

- issue-014 (medium): STAT 주문 여부가 Order.priority의 stat 값, Order.is_stat 플래그, StatOrder subtype 세 표면에 중복되어 있어 하나의 주문이 서로 다른 STAT 상태를 동시에 갖는 모순 인스턴스가 가능하다.
