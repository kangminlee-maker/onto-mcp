# Synthesize

## Consensus
- issue-001 (high): Window start and window close are judged on two different time authorities: enqueue binds windowStartedAt to the internal Date.now() wall clock while flush evaluates closure against an arbitrary caller-supplied now, and no same-clock precondition is declared. The claim set {C5 "flushes when the window has closed", C6 "[] means window still open", R1 internal-clock window start, R3 caller-clock close check} is jointly satisfiable only under the undeclared premise that the caller's now comes from the same clock as Date.now(), so the documented flush close obligation is violable over the full declared input domain of flush(now). All three lenses accepted the recorded root and kept severity high; the required fix is to unify the time authority and declare the clock-source contract.
  - root cause: Window-start and window-close use different time authorities (internal Date.now() vs caller-supplied now) with no declared same-clock precondition, so the flush close obligation is violable with declared-legal inputs.
  - materiality: The issue directly weakens the declared review goals of correctness and verifiability of the flush contract. The failure path is occupiable today with declared-legal inputs: any flush caller whose now is not sampled from the same wall clock that enqueue used (deterministic-clock tests, monotonic-time-derived values, cross-process or skewed clock sources) triggers it. The impact is that digests are never emitted for the affected window (a perpetual [] that the contract says means "window still open") or are emitted before the window elapses, so the 30s batching contract is silently broken and the documented [] meaning becomes permanently misleading. This presently occupiable failure path is the panel's high-severity calibration anchor.
  - action: Unify the time authority so window start and window close are judged on the same clock, choosing one of three variants: (a) parameterize enqueue on the same clock (enqueue(item, now)), (b) drop the now parameter and use Date.now() inside flush, or (c) inject a single clock function at construction that both methods use. In all variants, declare the clock-source contract on the API doc. Closure class is fix_now with closure obligation must_close_in_target: this is a current correctness blocker because the failure path is occupiable with declared-legal inputs today. Ordering matters in two ways recorded upstream: this clock-split defect enables issue-003's persistent misreading of [] (rel-005), and the generalizing single-time-authority root is tracked in issue-004, so the single-time-authority fix here is the unit that discharges this issue inside the target.

Today, under the synchronous realization, the documented invariant is false and the guarantee is vacuous and unverifiable; under any async/concurrent/re-entrant realization the behavior becomes silent notification loss, the exact failure the comment claims to exclude. Deliberation adopted a direction-neutral root (the documented preservation property has no implementing mechanism) and fixed severity at medium in one decision for the duplicate cluster issue-002/issue-005/issue-007; closure requires an explicit implement-or-retract decision before the next stage.
  - root cause: The flush reset clears the whole pending map instead of removing only the entries that were flushed into the digest, making the documented check-to-reset carry-over guarantee unsatisfiable whenever such an enqueue occurs.
  - materiality: The issue weakens the declared correctness goal (no silent notification loss) and the regression_risk goal. The failure condition is any realization in which enqueue can interleave with flush between the close check and clear(): an async refactor of flush, concurrent callers, or re-entrant enqueue. The impact is silent notification loss while the in-code documentation asserts the opposite guarantee, so future maintainers relying on the documented invariant will ship the loss without noticing. Severity was resolved at medium rather than high under the panel's impact-reachability calibration: the check-to-reset antecedent is unoccupiable with declared-legal inputs in the bounded synchronous target (unlike issue-001's input-reachable clock split), so the present harm is a false documented invariant — a verifiability/maintainability harm — with loss activation conditional on a future refactor.
  - action: Make the comment true or make it honest. Either implement the documented property — delete only the flushed entries (snapshot the digested keys/items, then delete those specific entries) so post-check arrivals genuinely persist into the next window — or retract it by rewriting the comment to state that the reset drops everything currently pending and that the implementation relies on synchronous execution to keep the check-to-reset interval empty. The ordering dependency is explicit in the framing: closure is gated by this implement-or-retract decision (closure_class needs_decision), because which side is defective is unverifiable within the bounded target, and the issue must close before the next stage (must_close_before_next_stage) — it blocks any async or re-entrant refactor of flush rather than current operation.
