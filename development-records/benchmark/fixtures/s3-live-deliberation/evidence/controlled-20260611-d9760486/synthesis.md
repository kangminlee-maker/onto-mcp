This is a high-severity, material correctness defect that must be closed in the target by binding the whole window lifecycle to one declared time authority.
  - root cause: Time authority is split across the two mutating entry points — the window anchor is sampled from ambient Date.now() at enqueue (line 20) while window closure is computed from the caller-injected now at flush (line 30) — and no declared contract binds the two clocks, so the closure rule's truth rests on an undeclared necessary condition. If binding both operands of the closure predicate to one declared clock authority removes the contradiction for all permitted inputs, the hypothesis holds; if the contradiction persists, it is refuted.
  - materiality: The issue strikes the declared review goal `correctness` on the core flush contract C4 inside the explicitly requested time-source-semantics focus. The signature flush(now: number) carries no time-base constraint, so any permitted caller whose now comes from a clock other than Date.now() — a test clock, monotonic clock, or replayed/skewed clock — triggers the failure: with a smaller-magnitude now the window never closes and flush returns [] forever, while with a larger-epoch now it flushes immediately. Either way the declared 30s digest behavior is unachievable for permitted inputs, so the primary batching contract cannot be trusted.
  - action: Adopt a single time authority for the whole window lifecycle — either thread the caller clock through both entry points (enqueue(item, now) or anchor the window from item.enqueuedAt) or use one injected/ambient clock for both — and declare the time-base constraint on the interface. The projected action class is fix_now with closure obligation must_close_in_target.
