# 구간 단위 배달 — 라이브 프로브 (2026-07-31)

이 트랙(S1~S6)의 **첫 라이브 실증**이다. 그 전까지는 전부 실 fixture와 실 전사본 replay였다.

```
npx tsx scripts/observation-read-pull-live.mts
```

실 `codex exec` 워커를 프로덕션 하드닝 그대로 띄우고, 실 59-관찰 코퍼스 위에 façade를 등록하고, 실 모델이
관찰을 가져가게 한다. OAuth 세션에서 실 디스패치 1회를 쓴다. 원본 증거는 `benchmark/`(gitignored) 아래
타임스탬프 디렉터리에 쌓이고, 여기 있는 것은 그중 **판정에 필요한 것만** 옮긴 것이다.

| 파일 | 무엇 |
|---|---|
| `delivery-verdict.json` | 재조정 판정 — 스키마 버전, 배달된 구간, attestation |
| `receipt.json` | façade 영수증 — 런타임이 **서빙한** 것 |
| `emitted-ranges.json` | 방출된 페이지의 **엔트리 shape만** (본문 제외, 4 MB → 1 KB) |
| `worker.json` | 워커 세션·전사본 결속 |

`source-observations.yaml`(3.9 MB)은 옮기지 않았다 — `scripts/fixtures/observation-catalog/`에 이미
커밋된 같은 코퍼스다. `descriptor.json`도 뺐다(런치 토큰을 담는다. 이미 죽은 값이지만 남길 이유가 없다).

## 무엇이 증명됐나

**codex-cli 0.145.0** — `VERIFIED_CODEX_CLI_VERSIONS`에 핀된 버전이라 재조정이 전사본을 수용한다.

- **페이지가 구간을 싣는다**: `part_allowance: 31253`(S4의 32,000 예산에서 프레이밍을 뺀 값),
  `body_start`/`body_end`, `range_content_sha256`, `range_id: orng_v1_…` — 전부 실 페이지에 실렸다
- **배달 레코드가 `observation-read-delivery/v2`**이고 `delivered`가 구간이다:
  `[[0, 3483]]` / `body_length: 3483`, `[[0, 10018]]` / `body_length: 10018`
- **`verbatim_delivered`** — 방출 정본이 워커 문맥에서 그대로 발견됐다. 재조정 4~5 ms
- 1-파트 관찰에서 `range_content_sha256 === observation_content_sha256`이다. 구간이 곧 본문 전체라
  그래야 맞는다 — 두 해시가 독립적으로 계산되므로 우연이 아니다

## 두 번 돌렸고, 첫 런이 결함을 찾았다

첫 런은 PASS했지만 로그에 `delivered = 2 observation(s): [object Object], [object Object]`가 찍혔다.
S2가 `delivered`를 id 배열에서 커버리지 레코드로 바꿨는데 프로브의 **단언은 고쳤고 로그 줄은 안 고쳤다.**
판정은 옳았지만 사람이 읽는 줄이 아무것도 보여주지 않았다 — 통과처럼 읽히는 침묵이다. 고친 뒤 두 번째
런에서 `obs_9f291d6235fdb41c [0,3483)/3483, obs_eb90f83378bd57a0 [0,10018)/10018`로 나온다.

**교훈**: 타입이 바뀌면 단언뿐 아니라 그 값을 **렌더링하는 곳**도 바뀌어야 한다. `join`은 객체 배열에서
조용히 무의미해지고, 그 무의미가 초록색으로 출력된다.

## 이 프로브가 덮지 않는 것

- **큰 관찰의 분할·재조립**: 여기서 가져간 둘은 3,483자와 10,018자라 각각 1파트다. 780 KB 관찰을 28파트로
  걷는 경로는 라이브로 돌린 적이 없다
- **부분 인용**: 워커가 관찰 일부만 읽고 그 구간만 인용하는 경로 — 즉 이 트랙의 **목적** — 는 라이브로
  미실증이다. 단위 테스트와 replay가 덮는다
- **S6의 judge 구간 투영**: 이 프로브는 answer-support judge까지 가지 않는다

# 2차: 페이징 arm (2026-07-31) — **F-3이 라이브로 실증됐다**

> ## ⚠ 정정 (2026-07-31, §3차) — 아래 "찾아낸 것" 절의 **진단과 수치가 틀렸다**
>
> 전사본을 원본에서 다시 재니 두 가지가 다르다. **F-3(병합)은 실재하고 실증됐지만, 승격된 이 런에서
> 일어난 일이 아니다.** 그리고 인용된 수신 레코드 크기는 어느 전사본에서도 재현되지 않는다.
> 아래 표는 두 런을 하나로 합쳐 적은 것이다. 정정 전문과 재현 방법은 **§3차**에 있다.

①② 를 넣어 프로브를 확장했다: **분할되는 관찰 하나**(`obs_020ed9af3779fd3d`, 82,717자, 32,000 예산에서
3페이지)를 골라 커서를 끝까지 걷게 했다. 증거는 `paging-run-*.json`.

## 통과한 것

- 3페이지 walk, 방출 크기 **31,951 / 31,955 / 29,236자** — 전부 예산 아래
- 영수증의 구간이 `[0, 82717)`로 병합되고 그 값이 아티팩트의 정규 본문 길이와 **일치**
- 민팅된 range id 3개가 `[0, 82717)`을 **순서대로 타일링** — 모든 문자에 인용할 이름이 있다
- 워커가 되돌려준 range id 전부가 방출 표에서 **해소**된다

## 그리고 찾아낸 것 — 절단의 단위는 페이지가 아니다

**방출 3건 전부 `verbatim_delivery_not_attested`.** 전사본을 직접 재보면:

| | |
|---|---|
| 보낸 MCP 결과 (`mcp_tool_call_end`) | 4 |
| 수신 레코드 (`custom_tool_call_output`) | **3** |
| 수신 레코드 크기 | **810 / 45,138 / 47,451자** |

개별 페이지는 31,955자로 **예산(32,000)과 관측 무손실 최대치(32,151) 아래**인데, 수신 레코드는
45,138·47,451자다. 여러 페이지가 **한 출력으로 병합**되어 `(32,151, 40,149]` 경계를 넘었고 잘렸다.

이것이 교차검증 보안 렌즈의 **F-3**이고 설계 `23-…md` §0-1의 정정이다. 그때는 논증이었고 이제 측정이다.

**시스템은 옳게 동작했다.** 도달하지 않은 내용을 인용 가능하다고 인정하지 않았다 — `delivered = 0`,
fail-closed 유지. 프로브가 이 경우를 결함이 아니라 **환경 한계**로 보고하도록 고친 이유다.

**처방**: 설계가 이름 붙인 프롬프트 지렛대 — **exec 턴당 도구 호출 1회**. 크기로는 못 닫는다(서버가
턴 경계를 못 보고, 누적 최악값으로 예산을 잡으면 하한 아래로 내려간다 — §3/S4의 표).

## 이 arm이 세운 대조군 넷은 전부 처음에 틀렸다

라이브가 아니면 못 잡았을 것들이다.

| 내가 단언한 것 | 왜 틀렸나 |
|---|---|
| 워커의 페이지 수 == 영수증의 호출 수 | 모델이 같은 호출을 반복할 수 있다(실측: 4호출 3구간). 영수증은 **호출**을, 워커는 **쓴 페이지**를 센다 |
| 워커가 인용한 tail == 정규 본문의 tail | 워커는 body를 **JSON 문자열 값**으로 받아 이스케이프된 형태를 인용한다 |
| tail 인용을 게이트로 | 같은 모델이 한 번은 맞추고 다음엔 본문 중간을 인용했다. 문자 단위 복사는 모델이 못 믿을 일이고, **재조정이 훨씬 강한 결정론적 검사**다 |
| 워커의 range id 수 == 페이지 수 | `PAGES: 3`이라 하고 id는 2개만 나열했다. 타일링은 **런타임 권위**로 옮겨야 한다 |

공통 교훈: **모델의 자기보고를 런타임 사실과 같다고 단언하지 말 것.** 각각이 다른 것의 권위다.

# 3차: 전사본 재측정 (2026-07-31) — **막고 있는 것은 병합이 아니라 봉투 크기다**

§2차는 자기보고를 믿지 말라는 교훈으로 끝났는데, 정작 그 절의 진단이 **전사본을 다시 재지 않고** 쓰였다.
다시 쟀고, 틀렸다. 표는 손으로 옮긴 것이 아니라 여기서 나온다:

```
npx tsx development-records/benchmark/20260731-range-delivery-live-probe/measure-received-records.mts \
  ~/.codex/sessions/2026/07/31/rollout-*-019fb710-*.jsonl \
  ~/.codex/sessions/2026/07/31/rollout-*-019fb712-*.jsonl \
  ~/.codex/sessions/2026/07/31/rollout-*-019fb6ac-*.jsonl
```

## 3-1. 두 런이 하나로 합쳐져 있었다

| 런 | 방출 | 수신(≥1KB) | 무엇이 일어났나 |
|---|---|---|---|
| 16:25 `019fb710` | 4 | **2** — 40,149 · 40,150 | 둘째의 원본 토큰 **22,943**(한 페이지의 ~16.7K를 크게 넘음) → **여러 페이로드가 한 레코드로 병합. F-3이 여기서 실증됐다** |
| **16:27 `019fb712`** (승격된 아티팩트) | 3 | **3** — 전부 40,149 | **페이지당 한 레코드.** 턴 간격 +6.1s · +4.8s. **병합 없음** |
| 14:36 `019fb6ac` (1차 arm) | 1 | 1 — 33,597 | 절단 없음 → `verbatim_delivered` |

§2차의 "보낸 4 / 받은 3"은 **16:25 런**의 수이고, 승격된 `paging-run-*.json`은 **16:27 런**의 것이다.
그리고 인용된 크기 **810 / 45,138 / 47,451자는 어느 전사본에도 없다** — 오늘 롤아웃 22개를 전수 스윕한
결과(인자 없이 같은 스크립트) 절단된 레코드는 **전부 40,149~40,153자**다. 45,138·47,451은 클립 지점보다
크므로 애초에 수신 레코드 크기일 수 없었다.

## 3-2. 그래서 무엇이 막고 있나 — 예산이 잘리는 대상을 재고 있지 않다

`observation-read-facade.ts:621-627`이 페이지를 **한 결과에 두 번** 싣는다 — `content[0].text`에
직렬화해서 한 번, `structuredContent`에 객체로 한 번. codex는 결과 객체 **전체**를 문맥에 렌더링하므로
실제로 절단되는 양은 페이지가 아니라 **봉투**다:

| 페이지(정본) | 렌더링된 봉투 | 배율 | 결과 |
|---|---|---|---|
| 15,528 | 33,550 | 2.161 | **도달** ✓ |
| 31,951 | 66,892 | 2.094 | 40,149로 절단 ✗ |
| 31,955 | 70,538 | 2.207 | 절단 ✗ |
| **29,236** | 66,414 | 2.272 | 절단 ✗ |

셋째 줄이 판정한다: **29,236자는 32,000 예산 아래인데도 실패했다.** 페이지 크기로는 이 넷이 갈리지
않고, 봉투 크기로는 40,149를 경계로 완전히 갈린다. 즉 S4의 32,000은 **봉투가 2.1~2.3배라 처음부터
도달할 수 없는 값**이었다.

**따라서 §2차의 처방 "exec 턴당 도구 호출 1회"는 이 실패를 고치지 못한다.** 16:27 런이 바로 그것을
했다 — 턴당 한 번씩, 5~6초 간격으로 — 그러고도 셋 다 잃었다. 병합은 실재하는 **별개의 잠복 위험**이지
지금 막고 있는 것이 아니다.

## 3-3. 이중 적재의 어느 쪽이 인증을 떠받치는가 — 지우려던 쪽이었다

`JSON.stringify(result.structuredContent) === canonical_text`가 **네 페이지 전부 true**다. 봉투가
렌더링될 때 `content[0].text`는 **이스케이프**되고(`{\"snapshot_digest\"…`) `structuredContent`는
**평문 JSON**으로 나오므로, `record.text.includes(canonical_text)`가 실제로 맞히는 것은
**`structuredContent` 사본**이다. → **중복이라고 `structuredContent`를 지우면 재조정이 죽는다.**
용량을 되찾으려면 지울 쪽은 `content[0].text`이고, 그건 표준 채널을 비우는 계약 변경이라 별도 결정이다.

절단은 middle-out이다 — 정본의 **머리 2,000자는 안 남고 꼬리 2,000자는 남는다**(이스케이프된 사본의
머리와 구조화 사본의 꼬리가 각각 살아남는다). 그래서 두 사본 중 어느 것도 온전하지 않다.

## 3-4. owner 결정 (2026-07-31): **비용 모델이 봉투를 세게 한다**

`splitBodyByJsonCost`가 "직렬화된 페이지 길이" 대신 "워커에게 렌더링되는 봉투 길이"를 세도록 바꾼다.
이스케이프가 필요한 문자를 2배로 계상하므로 **추정이 아니라 문자 단위 계산**이 되고, 전송 모양은
건드리지 않아 codex의 렌더링 동작에 새로 결속되지 않는다. 대가는 페이지가 ~17,600자로 작아져 큰
관찰의 호출 수가 두 배가 되는 것, 그리고 분할 경계가 이동하므로 **커서 버전 재승격**이 따라온다(F-8과
같은 이유). 설계 반영은 `design/20260727-…/23-…md` §0-1·S4.

## 3-5. 이 정정이 남기는 방법론 교훈

§2차는 "모델의 자기보고를 믿지 말라"로 끝났는데, 그 절 자체가 **전사본을 다시 읽지 않고** 요약 위에
쓰였다. 같은 함정의 한 층 위다.

- **완료 조건이 재는 것과 실패가 일어나는 곳이 다르면 통과해도 아무것도 보장하지 않는다.** S4의 완료
  조건은 "영수증이 `page_char_budget: 32000`을 적는가"였고 통과했다. 그런데 절단은 페이지가 아니라
  봉투에 일어나므로, 그 게이트는 결함이 있는 채로 초록일 수밖에 없었다. 라이브 프로브가 아니면
  안 잡혔다
- **수치를 인용할 때는 그 수치를 낸 산출물을 함께 못박는다.** §2차의 세 수치는 어느 런의 것도 아니어서
  재현이 안 됐고, 그것이 진단이 틀렸다는 첫 신호였다
