`source_observation_catalog_tool`을 repo settings에서 켜면 풀 층이 산다. 그 스위치 하나가

2. façade 풀 층(워커가 관찰을 직접 가져간다)
3. 전사본 확인 배달(인용 권위가 **배달뿐**이 된다. `served` basis는 삭제됐다)

되돌리기는 키 제거다. `source_delivery_reconciliation` 키는 **더 이상 존재하지 않는다** — 찾지 마라.

## 3. **켜기 전에 재야 할 것** — 비용축이 이동했다

설계 §0-3 정정이 남긴 숙제이고, S4′가 그걸 **더 무겁게** 만들었다. 페이지가 작아졌으므로 같은
코퍼스를 읽는 데 드는 호출 수가 늘었다.

이미 아는 실측 (`benchmark/20260731-range-delivery-live-probe/measure-rendered-budget.mts`):

| | |
|---|---|
| 코퍼스 전체 최대 렌더 결과 | **37,920자** = 예산의 99.8%, 실측 클립 40,149 아래 |
| 페이지→결과 비율 | **2.05~2.27배**(코퍼스 안에서 변한다. 이론 천장 3.00) |
| 호출 상한 32를 넘는 관찰 | **2건** (52페이지 · 38페이지) |
| 가장 큰 관찰(780,114자) | **한 세션에 전부 배달 불가** — 약 1.6M 렌더 vs 약 1.04M 천장 |

마지막 줄은 회귀가 아니다. 이전에도 불가능했고 **구 회계가 절반으로 과소계상해 가능한 것처럼
보였을 뿐**이다. 이 트랙의 방향(일부만 읽고 그 구간만 인용)과 정합한다.

**아직 안 잰 것 — 이게 승격 판단의 입력이다**:

- 밀집 요청(작은 관찰 다수)에서 엔트리마다 framing이 붙어 페이지 수가 **선형으로** 는다. 실 코퍼스
  16-id 요청 walk의 총 페이지·호출 수를 새 예산에서 다시 재라. 구 32,000 페이지 예산 기준 수치가
  설계 `23-…md` §0-2 표에 있으니 **그것과 나란히** 놓아야 의미가 있다
- 그 수가 호출 상한 32와 fetch 예산 중 **어느 쪽에 먼저** 닿는지
- 닿았을 때 워커가 받는 것은 `call_limit_exhausted` 또는 `fetch_budget_exhausted`이고, 둘 다
  *"Cite what you already fetched"*라고 말한다. **그 상태에서 저작이 성립하는지**는 미실증이다

## 4. 되풀이하지 말 것 — 이 트랙이 산 교훈

- **완료 조건이 재는 것과 실패가 일어나는 곳이 다르면, 통과해도 아무것도 보장하지 않는다.** S4의
  완료 조건("영수증이 예산을 적는가")은 통과했고 결함은 남았다. 절단은 페이지가 아니라 봉투에
  일어났기 때문이다
- **모델의 자기보고를 런타임 사실과 같다고 단언하지 마라.** ②의 대조군 넷이 전부 그래서 틀렸다
- **계약을 두 곳에 적으면 모델이 그 모순을 조용히 해소한다.** 형식 오류가 아니라 **빈 성공**이라
  게이트가 잡을 것이 없다
- **수치를 인용할 때 그 수치를 낸 산출물을 함께 못박아라.** 프로브 README §2차의 세 수치는 어느
  런의 것도 아니었고, 재현이 안 된다는 것이 진단이 틀렸다는 첫 신호였다
- **전사본을 mtime으로 고르지 마라.** 한 번 무관한 다른 세션을 읽었다. 내용(런치 토큰·관찰 id)으로
  결속하라
- **프로브 자신의 설정이 결함이 사는 곳이다.** `scripts/observation-citation-live.mts`에 쿼터 0짜리
  dry-run이 있다(`ONTO_CITATION_LIVE_DRY_RUN=1`). 그것이 **관측할 수 없는 것**(디스패처 내부의
  라우트 해석)도 스크립트 주석에 적혀 있으니 그 경계를 믿어라
