## 1. 왜 구간인가 — 세 문장

1. **exec 출력 천장 ≈40,150자**는 외부 제약이고 내릴 수만 있다. 그런데 **페이지 예산이 65,536자**라,
   가득 찬 페이지는 **어떤 단일 exec 출력에도 통째로 들어갈 수 없다.**
2. `delivered`는 **정본 전체가 하나의 수신 레코드에** 있을 것을 요구한다. 따라서 **천장을 넘는
   페이지는 모델이 아무리 성실히 읽어도 영구히 `not_attested`** — 결함이 아니라 두 상수의 산술이다.
3. 예산을 내리면 파트가 늘고, `coversWholeObservation`이 **모든 파트**를 요구하며, 호출 상한 32와
   부딪힌다. **단위가 "전체"인 한 어떤 상수 조합으로도 큰 내용은 벽을 만난다.**

→ 단위를 구간으로 내리면 **같은 메커니즘이 500자와 800KB를 모두 처리**한다. 특수 케이스가 없다.

## 2. 확정된 계약

```
(observation_id, observation_content_sha256, [start, end), range_content_sha256)
```

- 모델에게는 **불투명 id만**(`orng_v1_…`) 준다. 런타임이 해석한다 → 모델이 오프셋을 지어낼 수 없다
- `range_content_sha256`으로 인용이 **자기 검증적**이 된다
- **`part_index`로 지칭하면 안 된다** — 파트 경계는 페이지 예산이 만든 전송 아티팩트다

### 착수 전 반드시 알 것 — 오프셋은 산술로 안 나온다

내가 처음에 *"`(part_index, part_allowance)`에서 산술로 도출된다"*고 적었다가 **교차검증에 반박당했다.**
`splitBodyByJsonCost`는 문자 수가 아니라 **JSON 이스케이프 비용**으로 자르고 `codePointJsonCost`가
비균일하다(`"`·`\` = 2, `< 0x20`·surrogate = 6, 그 외 1). allowance도 요청 id 목록에 따라 달라진다.
→ **런타임이 오프셋을 명시적으로 페이지에 실어야 한다.** 페이지 계약 변경이며 공짜가 아니다.

### owner 결정 — 구조로 막지 않는 것

> *"관찰의 일부만 읽고 전체에 대해 주장했다면 논리 검증에서 막힌다. 구조적으로 막을 필요는 없다."*

배달 층은 **"이 바이트가 도달했는가"만** 답한다. 인용 범위의 정직성은 주장-증거 정합성 층이 맡는다.
지금은 배달 층이 "전체 도달 요구"로 그걸 우회 처리하고 있었고, **그게 크기 의존성의 원인**이었다.

## 8. 이 세션의 검증 교훈 — 반복된 것은 코드가 아니라 내 방법이었다

- **부재 주장은 전수 확인이 필요하다.** `head -20`에 잘린 목록에서 "테스트 없음"을 결론(중복 작성) ·
  판정 경로만 grep하고 `truncated`/`call_id`를 죽은 필드로 오진(**테스트가 증거로 읽는다**) ·
  커밋된 `PROVENANCE.md`를 안 보고 코퍼스를 다시 재서 틀림. **하루에 네 번, 전부 같은 모양.**
- **diff의 `-` 줄은 제거가 아니다.** 이동·시그니처 변경이 전부 `-`로 보인다. 5건 중 4건 오탐.
  신뢰할 수 있는 건 **두 시점의 이름 집합 차집합**이었다.
- **fixture 3벌은 전수가 아니었다.** "세 fixture 모두 일관됩니다"라고 측정 보고까지 하고 라이브를
  깨뜨렸다. 지금은 네 벌이고 넷째가 그 회귀를 잡는다.
- **수정에도 겨냥 리뷰를 다시 걸어라.** 수정은 옳았는데 그 회귀 테스트가 무효였던 적이 있다.
- **파이프의 `$?`는 마지막 단계 것이다.** `npm run … | head && echo $?`로 타입체크 통과를 오판했다.
