## 2. `runReconstruct`의 실제 형태

```
runReconstruct(params)                                   4,382줄
├─ 전문: 파라미터 + const/let 24개 + assembleGracefulTerminal 클로저(162줄)

```

바깥 스코프(파라미터 + 전문 선언) 이름 **49개**. try 안 최상위 이름 **239개**. 즉 이 함수는 **288개 이름이 한 스코프에 평평하게 누적되는** 구조다.

**최대 142개.** 중간 구간(300~3,700줄)에서 가장 싼 지점도 23개이고, 그마저 누적 3,655줄(=94% 지점)에 있다. **"파이프라인 단계별로 자른다"는 접근은 50~140개 인자를 넘기는 일이다** — 리팩터가 아니라 상태 객체를 발명하는 일이다. owner가 1차에 기각한 판단이 옳았다.

### 2.2 그러나 "이미 닫혀 있는 블록을 빼내는" 비용은 다르다

블록 하나를 함수로 빼낼 때의 실비용은 **입력(앞에서 선언됐고 그 블록이 실제로 쓰는 것) + 출력(그 블록이 선언하고 뒤에서 쓰이는 것)** 이다. 50줄 이상 닫힌 블록 전수 실측:

| 라인 | 줄 | 입력 | 출력 | 개념 |
|---|---:|---:|---:|---|
| L4321 | 52 | **2** | 1 | 시딩 레코드 artifact refs |
| L2604 | 60 | **6** | 0 | 환경 컨텍스트 프로파일 발화 (disclosure-only) |
| L3590 | 52 | **12** | 0 | 온톨로지 시드 검증 실패 경로 |
| **L2051** | **491** | **17** | **0** | **semantic-map 스테이지 실행 + dispatch fallback** |
| L4541 | 85 | 21 | 0 | 성숙 폐포 라운드 |
| L3222 | 63 | 37 | 0 | 목적 확인 대기 graceful 경로 |
| L3444 | 70 | 43 | 0 | 시드 저작 준비도 graceful 경로 |

| L4109 | 132 | 103 | 1 | 사전 발행 레코드 artifact refs |

**두 가지 결정적 사실:**

1. **출력이 전부 0~1개다.** 이 함수는 지역 변수를 새로 만들어 넘기지 않고, 누적된 상태를 **읽어서 파일로 쓴다**(write-through). 그래서 추출된 블록이 복잡한 튜플을 반환할 필요가 없다 — 분해가 구조적으로 가능하다.
2. **L2051 하나가 491줄인데 입력 17개다.** 함수의 11%를 파라미터 17개로 뗄 수 있다. 이게 최고 가성비다.

값싼 것은 대부분 **곁가지 경로**(환경 프로파일·검증 실패·graceful 경로·성숙 라운드)이고, 비싼 것은 전부 **최종 출력 조립 꼬리**(L4109 + L5121~L5357 = 420줄)로 누적 상태 깊숙이 있다.

## 3. 증명이 어떻게 바뀌는가 — 이게 이 설계의 핵심 위험이다

1~3차의 안전은 **바이트 동일성**에서 나왔다: `scripts/run-extraction-identity.mts`가 옮긴 심볼 본문이 `origin/main`의 원문과 바이트 동일함을 AST로 증명했고, 376심볼이 MODIFIED 0으로 통과했다. 분해는 순수 이동이 아니므로 **그 증명이 무효가 된다.**

무효화의 범위를 정확히 보자:

- **추출된 블록의 본문은 여전히 바이트 동일하게 유지할 수 있다.** 파라미터 이름을 원래 지역 변수 이름과 **똑같이** 두면 블록 텍스트를 슬라이스 그대로 옮길 수 있다. 즉 새 함수의 몸통은 원문과 한 글자도 다르지 않다.
- **바이트 증명이 사라지는 곳은 `runReconstruct` 본문 하나뿐이다** — 블록이 빠진 자리에 호출문이 들어가는 변경.

따라서 필요한 것은 두 가지다:

| 증명 대상 | 수단 |
|---|---|
| 추출된 블록 본문이 원문과 동일한가 | **새 검사 형태**: 블록 텍스트 동일성 검사기(§5.1). 현 검사기는 top-level 선언만 본다 |
| 래퍼 변경이 행동을 바꾸지 않았는가 | **행동 등가 하니스**(§5.2). 바이트로는 증명 불가 |

### 3.1 현 안전망 실측 — 지금은 부족하다

`runReconstruct`를 in-process로 완주시키는 테스트:

|---|---:|---:|---:|---:|
| `src/core-api/reconstruct-api.test.ts` | 1,058 | 27 | 7 | 2 |

완주 14회는 있지만 **최종 산출물에 대한 단정이 2건**뿐이다. 게이트 17종·vitest 3,689건은 "참조가 맞는가"를 지키지만, 오케스트레이터를 재구조화할 때 필요한 "산출물이 같은가"는 지키지 못한다. **이 공백을 먼저 메우지 않으면 분해는 증명 없는 변경이다.**

## 4. 옵션

### 옵션 1 — 하지 않는다 (기준선)

run.ts 5,723줄로 종결. 3차까지의 성과(원본의 26.5%)를 확정하고 제품 작업으로 넘어간다.

- **비용** 0. **위험** 0.
- **잃는 것**: `runReconstruct` 4,382줄은 계속 한 화면에 안 들어오는 함수로 남는다.
- **언제 맞나**: 규모축·가치벤치 같은 제품 본령이 급할 때. 이 함수를 자주 고치지 않는다면 합리적이다.

### 옵션 2 — Tier 1만 (권장 기본값)

입력 ≤17·출력 ≤1인 닫힌 블록 4개만 추출: **L2051(491) + L2604(60) + L3590(52) + L4321(52) = 655줄**.

- `runReconstruct` 4,382 → 약 3,730줄. run.ts 5,723 → 약 5,070줄.
- **블록 본문은 바이트 동일**하게 유지된다(파라미터 이름 = 원래 지역 변수 이름).
- 파라미터가 17개 이하라 **상태 객체라는 새 개념을 만들지 않는다** — concept economy 유지.
- 목적지: L2051은 `semantic-map-stage.ts`(이미 `runSemanticMapStage` 소유), L2604는 `environment-context-profile.ts`, L3590은 `ontology-seed-validation.ts`, L4321은 `record.ts`. **전부 3차에서 이미 append한 모듈** = 새 모듈 0개.
- **위험** 낮음. 되돌리기 = 커밋 revert.
- **선행 조건**: §5.2 등가 하니스. Tier 1도 래퍼는 바뀐다.

### 옵션 3 — Tier 1+2+3, 실행 컨텍스트 개념 도입

1,627줄(37%) 추출. Tier 2·3은 입력 21~103개라 `ReconstructRunContext` 같은 **명시적 실행 컨텍스트**를 도입해야 한다.

- `runReconstruct` 4,382 → 약 2,750줄. 하지만 **288개 평평한 이름을 컨텍스트 객체로 옮기는 것 자체가 큰 설계 변경**이다: 어떤 필드가 읽기 전용인지, 언제 채워지는지, 누가 소유하는지를 전부 정해야 한다.
- **위험 높음.** 바이트 증명이 블록 본문에만 남고, 컨텍스트 도입은 지역 변수 → 객체 필드 접근으로 **모든 참조 텍스트가 바뀐다**(`sourceObservations` → `ctx.sourceObservations`). 즉 Tier 2·3에서는 블록 본문 바이트 동일성도 포기해야 한다.
- **언제 맞나**: 이 오케스트레이터를 앞으로 자주 고칠 계획이고, 등가 하니스를 제대로 만든 뒤.

## 5. 구현 프로세스 설계 (옵션 2 기준)

### 5.1 단계 0 — 블록 텍스트 동일성 검사기 (선행, 필수)

현 `run-extraction-identity.mts`는 top-level 선언만 본다. 추출된 **블록**을 검사하려면 새 형태가 필요하다:

- 기준본 = `git show <pre-decomposition-ref>:src/core-runtime/reconstruct/run.ts`
- 선언한 각 추출에 대해 `{기준본 라인 범위 → 목적지 함수}` 를 받아, 목적지 함수 본문이 기준본 슬라이스와 **바이트 동일**한지 비교한다(들여쓰기 재정렬만 정규화).
- negative control: 블록 본문 한 글자를 바꾸면 FAIL해야 한다.
- **선언 목록에 항목이 0개면 FAIL**한다(공허 통과 방지). 2차·3차에서 게이트가 green인 채 커버리지를 잃은 유형을 여기서도 봉인한다.

### 5.2 단계 0.5 — 행동 등가 하니스 (선행, 필수)

§3.1의 공백을 메운다. `ONTO_LLM_MOCK=1` 결정론 경로로 `runReconstruct`를 완주시키고 **세션 루트의 산출 아티팩트 전체를 스냅샷**한다.

- **done-when(기계 판정)**: 분해 전 커밋에서 스냅샷을 뜨고, 분해 후 같은 입력으로 다시 떠서 **파일 목록과 각 파일 내용이 동일**함을 확인한다(세션 id·타임스탬프 같은 휘발 필드는 정규화 — 기존 `stripVolatileArtifactFields` 전례를 재사용).
- **falsifiable 확인**: 분해 전 코드에 의도적 1글자 변경을 넣어 하니스가 FAIL하는지 먼저 본다. **이걸 안 하면 하니스가 무엇도 증명하지 않는다.**
- 시나리오는 최소 2개: 정상 완주 1개 + graceful terminal 경로 1개(추출 대상에 graceful 곁가지가 포함되므로).
- 산출물은 `benchmark/` 또는 세션 디렉터리에 두고 커밋한다(replay 근거).

### 5.3 단계 1~4 — 블록별 추출 (배치 1개 = 블록 1개, 싼 것부터)

순서: `L4321(2)` → `L2604(6)` → `L3590(12)` → `L2051(17)`. 실패 시 되돌릴 표면이 작은 순서다.

배치마다:
1. 대상 블록의 입력·출력을 **다시 실측**한다(앞 배치가 스코프를 바꿨을 수 있다).
2. 블록 텍스트를 슬라이스로 옮기고, **파라미터 이름을 원래 지역 변수 이름과 동일하게** 둔다.
3. `check:ts-core` · `check:ts-scripts`
4. 전체 vitest — 3,689 pass·1 todo·**총계 일치**까지 확인한다(3차에서 중복 import가 테스트 12개를 침묵 스킵시켜 총계가 3,690→3,678로 줄었던 전례).
5. 블록 텍스트 동일성 검사기(§5.1)
6. 행동 등가 하니스(§5.2)
7. `check:*` 17종 — 15 green + G7·invariant-drift 2건(gitignored 잔해, 매번 `ignored=yes tracked=no`와 `src/`·`scripts/` 실위반 0 확인)
8. 죽은 import 정리 `scripts/run-dead-import-clean.mts`
9. 경로 명시 add → 커밋. **커밋 후** G4 재실행

### 5.4 게이트 재조준 주의 (1~3차에서 두 번 물렸다)

소스 텍스트를 스캔하는 게이트는 표면 이동을 따라가지 못하고 **실패하지 않으면서** 커버리지를 잃는다.

- 이동 후 `rg -c '\} catch' <목적지>` 로 catch 이동을 확인하고 `check-graceful-signal-rethrow.ts`의 `RUN_SURFACE_REFS`를 갱신한다. `MIN_GUARDED_CATCH_TOTAL`(현재 28)이 총량 하한으로 막아준다 — **green이라도 숫자를 확인하라.**
- **L2051은 중첩 try를 포함한다.** catch가 함께 이동할 가능성이 가장 높은 블록이다.
- 재조준한 게이트마다 negative control 2종(표면 드리프트용 + 의미 파괴용)을 붙인다.
- 동일성 검사기의 `APPEND_DEST_REFS`에 base-존재 목적지를 추가한다(항목별 침식 가드가 0개면 FAIL시킨다).

### 5.5 중단 조건 (redesign 트리거)

- 등가 하니스가 **negative control에서 FAIL하지 않으면** 중단한다. 증명 없는 상태에서 분해하지 않는다.
- 어떤 배치의 실측 입력이 **20개를 넘으면** 중단하고 owner에게 보고한다. 그건 Tier 1의 전제(상태 객체 불필요)가 깨졌다는 뜻이다.
- 로직 변경이 필요해 보이면 멈춘다. 1~3차의 계약과 동일하다.

## 6. owner 결정 사항

1. **어디까지 하는가** — 옵션 1(하지 않음) / **옵션 2(Tier 1 655줄, 권장)** / 옵션 3(1,627줄 + 실행 컨텍스트).
