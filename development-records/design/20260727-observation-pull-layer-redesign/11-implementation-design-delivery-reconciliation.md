## 0. 한 문장

**워커가 끝난 뒤, codex 자신의 rollout에서 "모델 컨텍스트에 실제로 들어간 바이트"를 읽어
전송분과 대조하고, 온전히 도달한 것만 `delivered`로 인정한다.**

> 이름 주의(§10-R2-3): `served`는 **전송 사실**로 이미 계약이 있는 이름이라 그대로 두고,
> 재조정 산출은 **`delivered`**라는 새 이름을 받는다. 아래 §2~§5의 서술은 그 개정을 반영한다.

## 1. 이 설계를 가능하게 한 실측 (본 세션)

### 1-1. rollout은 전송분과 수신분을 **둘 다** 기록한다

| 레코드 | 내용 | 65,553자 실행 | 128,049자 실행 |
|---|---|---|---|
| `event_msg` / `mcp_tool_call_end` | MCP 서버가 **보낸** 원본 | 9지점 전부(생존6+소실3) | 9지점 전부(생존4+소실5) |
| `response_item` / `custom_tool_call_output` | 모델 컨텍스트에 **들어간** 것 | 생존 6 · **소실 0** | 생존 4 · **소실 0** |

두 독립 실행에서 수신분 레코드가 내 quantile 측정과 **완전 일치**했다. 수신분 길이는 양쪽 다
**약 40,490자** — 실효 천장이 거기 있다.

### 1-2. 우리 디스패치에 결속할 수 있다

- **codex가 stderr에 `session id: <uuid>`를 출력한다.** 런타임은 이미 자식 stderr를 캡처하므로
  자기 id를 직접 얻는다. "최신 파일" 휴리스틱이 필요 없다.
- rollout 파일명에 그 uuid가 박혀 있고, 첫 줄 `session_meta`가
  `session_id` · `cwd` · **`cli_version`** · `git.commit_hash` · `git.branch`를 담는다 → 교차 확인과
  **버전 고정**의 재료.

### 1-3. 절단의 정체 — exec 출력 절단이다

모델은 MCP 도구를 직접 부르지 않는다. codex의 **JS `exec`** 안에서
`tools.mcp__<server>__<tool>(...)`를 호출한다(패킷 측정 제약 3과 일치). 따라서 결과는 exec의
출력 렌더링을 거쳐 컨텍스트에 들어가고, **exec 출력 상한**에 걸린다. 수신분 레코드에는
`Warning: truncated output (orig…` 문자열이 함께 남는다.

**설계에 미치는 영향**: 수신분은 페이지 JSON의 깨끗한 사본이 아니라 **모델이 쓴 JS의 렌더링 결과**다.
그러므로 대조는 "레코드 전체 다이제스트 일치"가 아니라 **"방출한 정본 페이지 문자열이 수신분 안에
온전히 들어있는가"**로 해야 한다(대상의 정확한 정의는 §9-F4 — "본문"이면 오귀속이 가능하다).
모델이 일부러 잘라 출력했다면 그것도 "도달하지 않음"이며, **그 판정은 의미상 옳다** —
컨텍스트에 안 들어간 것은 인용 근거가 될 수 없다.

## 2. 모양

```
디스패치 중 (기존 `served`의 뜻 그대로 + 기록 대상만 확정)
  façade → 페이지 서빙 → SERVED 기록 = 전송 사실 (기존 이름·기존 의미)
      + 방출된 정본 문자열 `JSON.stringify(page)` 그대로            ← 주장 아님, 입력임
      + 런치 결속 표식(원자적·선기록) · 감사 필드   (§10-R2-2 · R2-5)
      ※ 소비자가 읽을 수 있는 배달 영수증은 아니다 (§9-F3)

워커 종료 후 (신규, 런타임 부모)
  stderr에서 session id 확보 — CLI 기원 배너가 정확히 하나일 때만    (§9-M1)
    → rollout 파일 특정 · session_meta 검증(session_id·cwd·cli_version)
                          · 레코드 구조 적합성 검증                  (§9-M3)
    → 수신분 레코드의 실제 출력 페이로드만 파싱 — 짝짓기 없음        (§9-F1)
    → 각 emission 문자열이 그 페이로드 안에 온전히 있는가            (§9-F4)
    → 온전 도달한 방출분을 기존 누적·완전성 리듀서에 흘려
      **delivered** 산출        (§9-F2 · §10-R2-3 · 순서 비의존 §12-S4 · §6-4)
    → verified 일 때만 RECEIPT(v3) 발행 · 그 밖은 unverifiable       (§9-M2)

소비자 (규칙 무변경, 이름만 이동)
  observationIdsDelivered(receipt) — 완전 커버리지 투영. 접기 규칙은 한 글자도
  안 바뀌고, 읽는 필드가 `served`(전송)에서 `delivered`(도달)로 옮겨간다.
  진단 문구는 verified-empty와 unverifiable을 구별해야 한다              (§10-R2-4)
```

### 왜 이름을 새로 만드는가 (초안에서 뒤집힌 지점)

초안은 `served`의 **생산자를 하나로 줄인다**고 썼다 — 개념 순증 0이 목표였다. R2가 그 목표를
반박했다: `served`에는 이미 계약이 있고(`grant.ts:372-375`, *"records what the runtime SERVED,
not what the model read"*), 거기에 수신 기준을 덮어쓰면 `calls_served`·`chars_served`(전송
기준)와 뜻이 섞인 한 레코드가 된다. 개념을 아끼려다 **한 이름에 두 의미**를 넣는 쪽이 더 나쁘다.

- 실행 중 기록 = **`served`** — "보냈다"는 사실. 기존 이름·기존 의미 그대로. 여기에 방출 정본
  문자열과 런치 결속 표식·감사 필드가 함께 산다(§10-R2-2 · R2-5).
- 종료 후 재조정 = **`delivered`**의 **유일한 생산자**. 새 이름 하나가 순증한다.
- 접기 규칙 = **무변경**. 여전히 한 곳(§9-F2의 추출된 리듀서)에만 선언돼 있다.

즉 이 설계가 막는 "성질을 안 물려받은 두 번째 메커니즘"은 **규칙의 중복**이지 이름의 추가가
아니다. 규칙은 하나로 유지하고, 서로 다른 두 사실에는 서로 다른 이름을 준다.

## 3. Fail-closed 조건 (전부 "인용 0"으로 떨어진다)

소비자는 이미 *"영수증 없음 = 아무것도 서빙 안 됨"*으로 fail-closed다(facade.ts:766 — 실코드 확인:
`readObservationReadFacadeReceipt`는 파일 부재·JSON 파손·스키마 불일치·launch token 불일치를 전부
`null`로 떨어뜨리고 호출자에게 "아무것도 서빙 안 됨"으로 읽으라고 계약한다). 여기에 얹는다.

아래는 전부 **`unverifiable`**이며 — "배달이 없었다"가 아니라 "인정할 수 없다"다(§9-M2) — 유효
영수증(v3)이 만들어지지 않으므로 소비자 투영은 ∅(인용 0)이다.

| 조건 | 처분 |
|---|---|
| stderr의 CLI 기원 session id 배너가 0개 또는 2개 이상 | unverifiable → ∅ (§9-M1) |
| rollout 파일 없음/읽기 실패 | unverifiable → ∅ |
| `session_meta.session_id`·canonical `cwd` 불일치, 또는 생성 시각이 자식 수명 창 밖 | unverifiable → ∅ (§9-M1) |
| `cli_version`이 검증된 목록 밖 | unverifiable → ∅ (**버전 고정**) |
| 레코드 구조가 기대 형태와 다름(종류·필드 타입·페이로드 위치) | unverifiable → ∅ (§9-M3) |
| 방출 문자열이 인정된 무손실 렌더링 형태로 발견되지 않음 | 그 방출분만 미도달 (§9-F4) |
| 재조정 전 런타임 사망 | **§9-F3 참조 — 초안의 주장이 거짓이었다. 개정 후: emissions만 남고 유효 영수증 없음 → ∅** |

**원칙**: 모든 미지는 "덜 인정"으로 떨어진다. 잘못 인정하는 방향으로 깨지는 경로를 두지 않는다.
단, **인정 불가를 배달 사실로 기록하지는 않는다** — 운영 증거에는 원인이 남는다(§9-M2).

## 4. 도입되는 개념 (최소)

| 이름 | 소유하는 규칙 | 선언 위치 |
|---|---|---|
| `emissions` | façade가 **방출한 정본 문자열 그대로** (주장 아님). 런치 결속 표식·감사 필드를 함께 싣는다(§10-R2-2 · R2-5) | façade 세션 상태 + 전용 스키마 |
| `delivered` | 모델 컨텍스트에 **도달한** 관찰. `served`(전송)와 뜻이 다르므로 이름을 나눈다(§10-R2-3) | v3 영수증 |
| `DeliveryReconciliation` | rollout 수신분에서 `delivered`를 **유일하게** 파생. 결과는 `verified` 또는 `unverifiable` | 신규 순수 모듈 |
| `verified_cli_versions` | 어떤 codex 버전에서 이 파생을 신뢰하는가 | 설정/상수 1곳 |

`challenge` · `ack` · 새 도구 op는 **도입하지 않는다.** 도구 스키마 변경 0, 호출 예산 증가 0.

**개념 순증을 막는 두 가지 제약**(교차검증이 강제):

- `unverifiable`은 새 아티팩트 권위가 아니라 `DeliveryReconciliation`의 **결과 상태**다. 영수증을
  만들지 않으므로 소비자 표면에는 나타나지 않는다(§9-M2).
- 페이지 → `delivered` 접기는 **새로 쓰지 않는다.** 지금 인라인으로 있는 규칙을 **순수 리듀서로
  추출**해, 실행 중 계량과 재조정이 **같은 것을 import**한다. 규칙 선언은 여전히 한 곳이다(§9-F2).
  > **정정(2026-07-28 §6 재편)**: 그 규칙은 **한 곳이 아니라 두 곳**이다 — 누적은
  > `observation-read-grant.ts:663-686`, **완전성 판정**은 `observation-read-facade.ts:848-855`
  > (`observationIdsServed`의 필터). 추출 대상도 둘이다(§6-4).

## 5. 8개 실패 분류에 대한 처분

1. **증거 신원** — 재조정이 `session_id`·`cwd`·`git.commit_hash`로 결속 + **배너 유일성·시간창**(§9-M1). 다른 디스패치의 rollout은 불일치로 탈락. **한 곳 검사**
2. **보냄 vs 받음** — 이 설계의 본론. 두 사실이 **다른 이름**을 갖고(`served`/`delivered`), 후자가 **수신분**에서만 파생된다. **표현 불가**
3. **완전성** — 기존 완전 커버리지 투영 유지 + **정본 페이지 단위** 온전 존재 확인(§9-F4) + 접기는 기존 리듀서 한 벌(§9-F2). **표현 불가**
4. **모든 결과 계량** — 기존 예산 기계 그대로(변경 없음). **기존 상태 유지**
5. **종결 상태** — 기존 latch 그대로. **기존 상태 유지**
6. **에러 채널** — 변경 없음(재조정은 워커에게 아무것도 안 보낸다). **기존 상태 유지**
7. **재개·재사용** — 재조정 산출이 영수증이고, 재사용 키가 이미 영수증을 본다. **한 곳 검사**
8. **한 규칙 두 선언** — 접기 규칙의 선언을 하나로 줄인다(§9-F2). 이름은 `delivered` 하나가 순증하지만 그것은 **다른 사실**이다(§10-R2-3). **개선**

### 6-1. 의존 그래프 (무엇이 무엇의 전제인가)

```
A (S1 닫기)  ─── 독립. 재조정과 무관하게 단독 가치. 그러나 재조정보다 반드시 먼저.

0 (추출)  →  0b (순서 비의존)  →  2 (재조정기)

2  →  [3 + 4]  ← 원자. 4 없이 3만 도달 가능해지면 안 된다 (D3=②).
```

| 단계 | 내용 | 검증 (done-when) |

커밋과 게이트 커밋이 갈라져서는 안 된다** — 갈라지는 순간 `default-off`가 `unreachable`인 척한다.

### 6-3. 단계 A — 복구 턴을 결정론 구문 수리로 (D2=a)

지금 `authoring-llm-call.ts:307-333`은 파싱 실패 시 **2차 LLM 디스패치**를 돌린다. 프롬프트는
"구두점만 고쳐라"라고 말하지만 **런타임이 그것을 강제하지 않는다** — §12-S1이 실코드로 확인했고,
`observation-read-pull.test.ts:376-448` 픽스처가 그 위반을 **성공으로 단언**한다.

**교체 대상은 좁다.** `parseLlmJsonObject`(:86-108)가 이미 결정론 층을 갖고 있다 — 코드펜스 제거 +
첫 `{`~마지막 `}` 절단. LLM 턴이 잡는 나머지는 (i) 문법 오류(후행 쉼표·따옴표 미이스케이프)와
(ii) **max_tokens 절단**이다. (i)은 결정론으로 고칠 수 있고, (ii)는 **꼬리가 실재하지 않으므로
아무도 고칠 수 없다** — LLM 턴은 그것을 "고치는" 게 아니라 **지어낸다.** 그것이 S1의 정체다.

- **불변식(증명 대상)**: 산출 객체의 모든 리프(문자열·수·불리언)가 **입력 텍스트에 verbatim으로
  존재**한다. 새 키·새 스칼라 0. 잘린 꼬리의 불완전 원소는 **버린다**(발명하지 않는다).
- **행동 변화(= owner가 승인한 비용)**: 지금 LLM 복구가 살려내던 런 일부가 실패로 떨어진다.
  특히 절단된 출력. 이것은 손실이 아니라 **거짓 성공을 실패로 되돌리는 것**이다.
- **파급 — L3의 뿌리가 함께 닫힌다.** 2차 자식이 사라지므로 "산출물 하나 = 자식 하나"가
  복원되고, §11-L3이 요구한 "배너 규칙을 자식 단위로 다시 쓰기"가 **이 경로에서는 불필요**해진다.
  ⚠ 이것을 **주장으로 두지 않는다**: `callLlmRecorded`(:150-240)는 호출당 정확히 1회 디스패치하고
  재시도가 없으며, `callJsonAuthor` 호출부 19곳 중 **façade를 싣는 곳은
  `direct-call-directive-author.ts:3383` 하나뿐**임을 확인했다(제품 코드 전수 검색). 그럼에도 다른
  경로의 2차 자식 부재는 **테스트로 못박는다** — *façade를 실은 디스패치는 산출물당 정확히 1회*.
- **픽스처 뒤집기**: `observation-read-pull.test.ts:376-448`은 현재 1차 `"{ not json"`(내용 전무)

  **실패**여야 한다. 테스트의 거짓 전제 주석(*"복구는 JSON을 재포맷할 뿐"*)도 함께 고친다.

### 6-4. 단계 0 / 0b — 추출은 두 곳, 순서 비의존은 별도

**초판 정정**: §9-F2와 §4는 누적 규칙을 `grant.ts:663-686` **한 곳**으로 적었다. 실측하면 **두
곳**이다 — 누적(어느 파트를 봤나, allowance-키 last-wins)은 `grant.ts:663-686`, **완전성 판정**
(`1..part_count`를 다 채웠나)은 `observationIdsServed`(`facade.ts:848-855`)의 필터에 있다.
재조정이 `delivered`를 만들려면 **둘 다** 필요하므로 추출 대상도 둘이다. 한 곳만 추출하면
"규칙 선언은 한 곳"이라는 §9-F2의 성질이 **완전성 쪽에서 조용히 깨진다.**

**0b가 필요한 이유 — 순서 의존은 재조정만의 문제가 아니라 이미 실행 중 경로에 있다.** 현 규칙은
allowance가 바뀌면 이전 인덱스를 버린다. 그래서 같은 페이지 집합이 **도착 순서에 따라 다르게
판정된다**: `A(allow=X, 1/2)` · `A(allow=Y, 1/1)` · `A(allow=X, 2/2)`는 지금 거부되지만, 마지막
둘의 순서만 바꾸면 인정된다. 두 결과 모두 "발명"은 아니나 **하나는 참인 배달을 거짓으로 거부한다.**

**형태**: `(observation_id, sha256, part_allowance)` 파티션을 **모두** 추적하고, 그중 **하나라도
완전하면** 인정한다.

**안전성 — 이 형태는 방어 성질을 잃지 않는다.** 현 주석이 근거로 드는 실측 사례(grouped 1/2가
64,774에서 끝나고 solo 2/2가 65,068에서 시작, 293자 구멍)는 순서 비의존 형태에서도 **여전히
거부된다**: 두 파트가 서로 다른 allowance에 속하므로 어느 파티션도 완전하지 않다. 사라지는 것은
"나중 allowance가 먼저 것을 버린다"는 **순서 부수효과뿐**이고, 파티션 경계는 그대로다.

**검증에 음성 대조를 넣는다**: 파티션 키에서 `part_allowance`를 빼면 293자 구멍이 통과해야 한다.
통과하지 않으면 그 테스트는 자기가 지킨다고 주장하는 것을 지키지 않는 것이다.

### 6-5. 단계 2의 강점과 그 한계 (초판에서 유지)

## 7. 해결하지 못하는 것

- **배달 ≠ 주의.** 바이트가 컨텍스트에 들어갔음을 증명할 뿐, 모델이 읽었음이 아니다.
- **버전 취약성.** 문서화되지 않은 내부 아티팩트에 의존한다. 완화는 버전 고정 + fail-closed이지 제거가 아니다.
- **codex 이후의 변형.** 컨텍스트 진입 후의 압축·축약은 보이지 않는다.
- **인용의 타당성.** 인용이 주장을 실제로 뒷받침하는지는 이 층 밖이다.
- 원자 프레임(A)을 **대체하지 않는다.** 안 잘리게 하는 것이 여전히 1차 방어이고, F는 그 실패의 탐지기다.

### F3 — 충돌 전 사망이 fail-open이었다 (BLOCKER · 실코드 확인함)

초안 §3은 "재조정 전 사망 → 영수증 미기록 → ∅"이라고 썼다. **거짓이다.**
`facade-server.ts:114`가 매 응답마다 `session.commit()`으로 영수증을 **증분 기록**하고,
스키마 `observation-read-facade-receipt/v2`에 **완료 표식이 없다.** 따라서 재조정이 돌지 않으면
**emit 기반 영수증이 그대로 권위로 읽힌다.**

**처방(구조로)**: façade는 `served` 영수증을 **아예 쓰지 않는다.** 실행 중에는 `emissions`를 별도
스키마로 기록하고, `served` 영수증(v3)은 **재조정만** 쓴다. 소비자는 v3만 받는다.
→ 사망 시 유효 영수증이 존재하지 않으므로 ∅. 규약이 아니라 **스키마로** 막힌다.
→ 부수 효과: `served`의 생산자가 하나라는 성질이 파일 수준에서도 성립한다.

### F2 — 새 생산자가 기존 누적 규칙을 물려받아야 한다 (BLOCKER)

재조정이 파트 인정 규칙을 **다시 유도하면**, 실제로 보지 못한 중간 구간을 "완전 수신"으로
조립할 수 있다.

**주 세션이 실코드로 확인함**(리뷰어 지적도 가설이므로): `observation-read.ts:518`의
`splitBodyByJsonCost(body, allowance)`가 파티션 함수이고, 주석이 *"분할은 `(body, allowance)`만의
함수"*임을 명시하며, `allowance`는 **요청에서 파생**된다(:188). 즉 **파트 신원이 요청에 의존한다** —
이 트랙이 `part_count`로 두 번 헛짚은 바로 그 자리다. 서로 다른 allowance로 나온 파트를 섞으면
인덱스가 대응하지 않으므로, 재조정이 재분할하면 **다른 분할의 조각들로 완전 커버리지가 조립될 수 있다.**

**처방(리뷰어 제안보다 강하게)**: "같은 함수를 import"가 아니라 **재조정이 분할 산술을 아예 하지
않는다.** `emissions`는 façade가 **실제로 방출한 정본 문자열 그대로**를 기록한다(§9-F4). 재조정은
오직 *"이것이 컨텍스트에 온전히 들어갔는가"*만 묻는다. 재분할도, 파트 인덱스 재계산도, allowance
재유도도 없다. 파티션 산술은 이미 그것을 소유한 곳(façade/grant)에 그대로 남는다.
→ 규칙을 공유하는 것이 아니라 **오류 클래스를 제거한다.**

**다만 접기는 남는다 — 전문 리뷰가 여기를 정확히 짚었다.** 도달분에서 `served`를 만들려면
"파트를 언제 합쳐도 되는가"를 여전히 누군가 적용해야 하고, 그 규칙은 지금
`observation-read-grant.ts:663-686`에 **인라인으로** 있다(실코드 확인: `existing.partAllowance ===
entry.part_allowance`일 때만 기존 레코드를 잇고, 아니면 이전 인덱스를 **버린다** — 주석이 그 근거로
"grouped 1/2가 64,774에서 끝나고 solo 2/2가 65,068에서 시작하는데 둘 다 count 2를 보고한다,
합치면 293자 구멍 위에 완전 커버리지를 주장한다"는 실측을 든다).

→ **단계 0에서 그 누적을 순수 리듀서로 추출**하고, 실행 중 계량과 재조정이 **같은 것을 import**한다.
재조정은 도달분을 **방출 순서대로** 그 리듀서에 흘릴 뿐 규칙을 다시 쓰지 않는다. 재구현하면
리뷰어가 든 시퀀스가 그대로 성립한다.

> **정정 2건(2026-07-28 §6 재편)**: ① 추출 대상은 **두 곳**이다 — 누적(`grant.ts:663-686`)과
> **완전성 판정**(`facade.ts:848-855`). 하나만 추출하면 "선언은 한 곳"이 완전성 쪽에서 조용히
> 깨진다. ② "**방출 순서대로** 흘린다"는 부분은 §12-S4가 반박했다 — 서버의 기록 순서는 모델이
> 본 순서가 아니다. 리듀서를 **순서 비의존**으로 만든다(단계 0b, §6-4).

F1의 처방과 같은 곳으로 수렴한다: **재조정 = 기록된 정본 문자열에 대한 포함 검사 + 기존 리듀서
호출, 그 이상 아무것도 아니다.**

### F1 — 순서 짝짓기는 즉시 어긋난다 (리뷰어 BLOCKER · 주 세션도 사전 지목)

한 `exec` 안에 MCP 호출이 여러 개면 순서 짝짓기가 깨진다. 실제로 관측된 호출 패턴이다.
리뷰어의 시퀀스: 외부 exec E1이 M1·M2를 부르고 출력 O1 하나를 내면, E2가 M3을 부르고 O2를 낸다.
서수 짝짓기는 M1→O1, M2→O2, M3→∅이 되어 **실제로 도달한 M2·M3을 놓친다**(방향은 보수적이지만
"정확한 도달 집합"이라는 요구는 깨진다).

**처방: 짝짓기를 없앤다.** 우리가 묻는 것은 "이 방출분이 모델 컨텍스트에 들어갔는가" 하나뿐이다.
→ 그 세션의 **모든 수신분 레코드를 통틀어** 각 방출 정본 문자열(§9-F4)의 온전 존재를 확인한다.
레코드 대응이 필요 없다. 다른 경로로 그 문자열이 컨텍스트에 들어갔더라도 **들어간 것은 사실**이므로
판정은 여전히 옳다.

### F4 — 포함 검사의 대상이 "본문"이면 오귀속이 가능하다 (BLOCKER · 실코드로 대상 확정함)

리뷰어: containment의 대상이 관찰 본문이나 파트 조각이면, 우연히 일치하는 소스 텍스트가 **다른
관찰의 조각을 이 관찰의 도달로 귀속**시킬 수 있다. 대상은 snapshot digest·observation id·content
hash·part index/count/allowance·body·cursor를 **전부 포함한 완전 정본 페이지**여야 한다.

**주 세션 확인 — 그 정본은 이미 존재하고, 필드 집합이 정확히 일치한다.**
`observation-read-facade.ts:511`이 워커에게 돌려주는 것은
`content:[{type:"text", text: JSON.stringify(page)}]`(같은 객체를 `structuredContent`로도 실음)이고,
`ObservationReadPage`는 `snapshot_digest` · `entries[]` · `next_cursor`를, 각 엔트리는
`observation_id` · `observation_content_sha256` · `part_index` · `part_count` · `part_allowance` ·
`body`를 담는다(`observation-read.ts:178-204`). 즉 리뷰어가 요구한 것은 **새 직렬화가 아니라
방출된 그 문자열**이다.

**처방**: `emissions`는 다이제스트나 재구성물이 아니라 **방출된 `JSON.stringify(page)` 문자열
그대로**를 기록한다. 재조정은 JSONL 봉투를 파싱해 **실제 출력 페이로드 안에서만** 그 문자열을
찾고, 무손실이라고 검증된 소수 렌더링 형태만 인정한다(그 문자열이 그대로 나타나는 경우 —
`text(r.content[0].text)` · `text(r.structuredContent)` 등). pretty-print · 부분 투영 · base64 ·
그 밖의 미지 변형은 **미도달로 떨어뜨린다**. 전사본 전체를 문자열 검색하지 않는다.

→ 오차의 방향이 한쪽이다: 미지의 렌더링은 **거짓 음성(덜 인정)**만 만들고 거짓 양성을 못 만든다.
정본 전체가 수신분에 나타났다면 그 정보는 실제로 컨텍스트에 들어간 것이므로, 우연 일치도 무해하다.

### M1 — 세션 결속은 배너 유일성까지 요구한다 (MATERIAL)

`cwd`와 `cli_version`은 여러 세션이 공유한다. stderr가 모호해 **옛 UUID**를 집으면 그 rollout의
`session_meta`는 자연스럽게 UUID·cwd·버전이 전부 일치하고, 반복 코퍼스의 페이지가 포함 검사를
통과할 수 있다.

**처방**: CLI 기원 배너가 **정확히 하나**일 때만 진행한다(0개·2개 이상 = unverifiable). 더해서
rollout 생성 시각이 자식의 수명 창 안일 것, canonical cwd 일치, `session_meta` 정확 일치를 요구한다.
**"첫 UUID 유사 문자열" · "최신 일치 rollout" 선택은 금지**한다 — 그게 바로 §1-2에서 필요 없다고
쓴 휴리스틱이다.

### M2 — 인정 불가와 "배달 없음"은 다르다 (MATERIAL)

rollout이 지워졌거나 읽히지 않아도 페이지는 **실제로 도달했을 수 있다.** 그 상황에서 `served=[]`를
배달 사실로 기록하면 거짓이다 — 인정 가능한 집합으로는 옳지만, 사실 기록으로는 틀린다.

**처방**: 재조정 결과를 `verified` / `unverifiable` 두 상태로 남기고, **권위 영수증(v3)은 verified
일 때만** 만든다. 소비자 투영은 그대로 ∅(인용 0)이므로 안전성은 동일하고, 운영 증거에는 원인이
보존된다. `unverifiable`은 새 개념이 아니라 `DeliveryReconciliation`의 결과 상태다(§4).

### M3 — 버전 화이트리스트만으로는 부족하다 (MATERIAL)

같은 버전 안에서도 설정·기능 조합에 따라 전사본 모양이 달라질 수 있다.

**처방**: 수용하는 rollout마다 **런타임 구조 적합성**을 검증한다 — 레코드 종류, 필드 타입,
가정한 순서/위상, 수신분 페이로드의 위치. `session_meta.cli_version`으로 자식의 실제 버전을 확인하고,
가능하면 디스패치 전에 미지 버전을 거른다. 구조가 다르면 버전이 목록 안이어도 unverifiable이다.

### M4 — replay 2벌은 위험 위상을 반증하지 못한다 (MATERIAL · 리뷰어 근거는 부정확, 지적은 유효)

리뷰어는 "저장소의 벤치 불변식이 **≥3런 × ≥2 fixture**를 요구한다"고 썼다. **저장소 문구는 그게
아니다**(실코드/문서 확인): `AGENTS.md:25-26`는 *"비교 실험은 한 번에 한 변수만 바꾼다. 결정 근거
수치에는 반복 횟수·fixture 수·분산을 반드시 병기한다. 표본 1회는 예비 관찰이며 결정 근거로 쓰지
않는다"*이고, 그 조항은 **비교 실험**에 관한 것이다. 재조정 replay는 비교 실험이 아니라 실 아티팩트에
대한 결정론 재생이므로 반복 횟수 자체가 쟁점이 아니다. 리뷰어의 인용은 채택하지 않는다.

**그럼에도 지적은 유효하고, 정확한 형태는 반복이 아니라 위상 커버리지다.** 오늘 확보한 실행 2개는
둘 다 `exec` 1회당 MCP 호출 1회 위상이다. "exec당 호출 1개"를 가정한 파서는 두 fixture를 **둘 다
통과**한다 — 즉 §6이 말한 "결정론적 반증 가능"은 확보된 위상 안에서만 참이다.

**처방**: 단계 1의 fixture에 **위상**을 넣는다 — 한 exec 안 다중 순차 호출 · 동시 호출 · 다중
`text()` 호출 · 겹치는 외부 exec · 호출 0회. 그리고 각 fixture에 **알려진 답**(어느 방출분이
도달했는지 독립 측정)이 붙어야 한다. 위상이 없으면 그 위상에 대해서는 **미검증으로 계상**한다.

## 8. 남은 측정

1. **직접 MCP 호출 경로가 있는가.** 모델이 exec을 거치지 않고 도구를 부를 수 있다면 exec 출력 상한을
   피할 수 있고, 절단 문제 자체가 축소된다. **우선순위 최상** — 그 경우 A의 상수가 크게 완화된다.
2. **exec 출력 상한의 정확한 값과 단위.** 수신분이 양쪽 다 ≈40,490자였다 — 상수인지 확인.
3. **절단 비결정성**(10 §2). F가 있으면 블로커는 아니지만 마진 산정에 필요.
4. `custom_tool_call_output`과 `mcp_tool_call_end`의 **짝짓기 규칙** — call_id 공간이 다르다(exec 스코프 vs
   도구 호출). 현재는 순서 의존이며, 다중 호출이 한 exec 안에 섞일 때의 규칙이 미확정.
   → §9-F1의 처방(짝짓기 제거)을 택하면 **설계 전제에서는 빠지지만**, 위상 fixture를 만들려면
   여전히 측정해야 한다(§9-M4).
5. **rollout 영속을 끄는 플래그**가 프로덕션 경로에 유입될 수 있는가(현재 `--ephemeral` 미사용).
6. **flush 타이밍** — 워커 종료 시점에 rollout이 완전히 기록됐는가.

### 전문 리뷰가 추가로 요구한 측정 (2026-07-28 반영)

위 6건과 겹치지 않는 것만 옮긴다. 리뷰어 목록 10건 중 1·2는 위 2·4와 같은 항목이고, 나머지는:

7. **수신분 렌더링의 실제 모양** — `text(r)` · `text(r.content[0].text)` · `text(r.structuredContent)` ·
   배열 · pretty JSON · 다중 `text()` · 유니코드/제어문자. 어느 것이 §9-F4의 "무손실 인정 목록"에
   들어가는지, 그리고 절단이 **항목별인지 exec 출력 총합인지**.
8. **세션 결속의 경계 조건**(§9-M1) — 동시 codex 자식, 중복/잡음 배너, `CODEX_HOME` 오버라이드,
   심볼릭 링크 cwd, 날짜 경계.
9. **실패 창**(§9-M2의 unverifiable 분기) — codex 비정상 종료, 타임아웃/SIGKILL, MCP EPIPE,
   JSONL 꼬리 절단, rollout 삭제, 재조정 예외, 영수증 발행 직전/직중 런타임 사망.
10. **재조정 → `served` 접기의 경계**(§9-F2 리듀서) — 재조회, 중복 페이지, 요청 id 집합 변경,
    서로 다른 `part_allowance`, 순서 뒤바뀜, **누락 파트의 모든 위치**.
11. **구조 게이트의 변이 배터리**(§9-M3) — 스키마를 의도적으로 변형해 게이트가 자기가 강제한다고
    주장하는 의존을 **하나씩 실제로 거부하는지**. 거부하지 않는 변이는 게이트에 대한 발견이다.
12. **OFF 경로 정확 스냅샷** — stdin·argv·환경/설정 인자·자식 수·생성 파일이 default-off에서
    불변임을 증명(단계 3의 byte-identical 요건과 같은 것).
13. **실 종단 `AnswerSupportLedger` 실행** — 도달한 인용은 통과하고 절단된 인용은 실제 codex 경로에서
    실패하는지. 리뷰어는 코퍼스 2벌을 제안한다.

리뷰어의 "저장소 불변식이 ≥3런 × ≥2 fixture를 요구한다"는 인용은 **부정확해 채택하지 않았다** —
근거와 대체 요구는 §9-M4에 적었다.

### R2-3 — `served`를 재정의하지 말고 `delivered`를 새로 만든다 (설계 골격 변경)

§2·§4는 `served`의 **생산자를 하나로 줄인다**고 썼다. 리뷰어 지적: 그 이름은 이미 계약이
있다. `observation-read-grant.ts:372-375`가 명시한다 — *"Named honestly: this records what the
runtime SERVED, not what the model read (design §7)."* 즉 `served`는 **전송 사실**이고, 거기에
"모델이 실제로 받은 것"을 덮어쓰면 한 레코드 안에 뜻이 다른 필드가 섞인다(`calls_served`·
`chars_served`는 전송 기준인데 `served` 목록만 수신 기준).

**처방**: 전송 사실은 `served`로 그대로 두고(내가 `emissions`라 부른 것이 이미 이 이름을
갖고 있다), 재조정 산출을 **`delivered`**로 새로 이름 붙인다. 소비자는
`observationIdsDelivered`로 옮기고, 재조정이 그 유일한 생산자가 된다.
→ 새 이름 하나가 늘지만 **기존 용어의 뜻을 조용히 바꾸지 않는다.** §9-F3의 "façade는 영수증을
안 쓴다"는 성질은 유지된다 — façade는 `served`(전송)를 쓰고, `delivered`는 재조정만 쓴다.

### R2-2 — 영수증은 증거이자 **래치**였다

실코드 확인: `observation-read-facade.ts:452-462`의 생성자가 우리 launch token으로 영수증을
읽어 **존재하면 기동을 거부**한다(*"one launch serves one dispatch"*). 바로 아래에서 서빙 전
**개시 영수증**을 먼저 쓰는데, 주석이 그 목적을 *"granted, served nothing"을 "facade가 아예
안 돌았다"와 구별하기 위함*이라고 적는다. 즉 영수증이 세 역할을 겸했다: ①서빙 증거
②재기동 래치 ③실행 표식. §9-F3은 ①만 옮기고 **②③을 소리 없이 지웠다.**

**처방**: emissions 아티팩트가 ②③을 물려받는다 — 런치에 결속된 표식을 **원자적으로 먼저
생성**하고, 같은 런치의 두 번째 기동은 grant를 minting하기 전에 실패한다. 방출 순서는 단조
증가로 보존한다(§9-F2의 리듀서가 순서에 의존한다).
→ 부수 확인: ③의 구별은 리뷰어들이 요구한 **verified-empty vs unverifiable**과 같은 것이다.
이미 있던 성질을 지웠다가 되사는 셈이므로, 새 개념이 아니라 이전된 성질로 적는다.

### R2-5 — 옮길 것은 페이지 문자열만이 아니다

현 영수증은 `rejected_before_grant` · `failures`(사유+상세, 앞뒤 양끝 보존) ·
`dropped_failure_count`를 싣는다(`facade.ts:247-265`). 주석이 그 값을 *"아티팩트를 못 읽었다"가
막다른 길 대신 진단이 되는 자리*라고 규정한다. 방출 **성공분**만 적는 emissions는 이것을
잃는다 — 예: `artifact_malformed`로 한 건도 방출되지 않은 런은 "verified, 배달 0"으로만 남고
원인이 사라진다.

**처방**: 이 감사 필드들을 런치 결속 emissions/감사 아티팩트에 함께 옮긴다. **단, 배달
재조정에는 참여시키지 않는다** — 전송·실패 기록이 도달 판정에 섞이면 R2-3이 지적한 혼합
권위가 다른 문으로 들어온다.

### R2-4 — 판정은 옳고 **진술이 틀린다**

`direct-call-directive-author.ts:3450`이 인용 거부 시 *"cites observation ids the runtime **never
served**"*라고 단정한다. `unverifiable`(전사본을 못 읽음)일 때 이 문장은 사실이 아니다 —
도달했을 수 있으나 확인할 수 없는 것이다. 인용을 막는 판정은 옳고 진술만 틀린다.

**처방**: 재조정 결과를 판별 가능한 형태로 진단 경계까지 전달해, *"확인 불가"*와 *"확인했고
배달되지 않음"*을 다른 문장으로 말한다. 소비자의 **투영은 그대로 ∅**(§9-M2) — 바뀌는 것은
메시지뿐이다.

### R2-1 — 단계 3은 단계 4 없이는 도달 불가여야 한다

리뷰어 시퀀스: codex가 rollout 모양을 바꿔 한 레코드 안에 **잘린 모델-가시 출력과 온전한
진단 형제 필드**가 함께 놓이면, 느슨한 스캐너가 형제 쪽에서 문자열을 찾아 영수증을
발행한다. 또 **수용된 최종 응답 이후에 기록된 출력**은 세면 안 된다.

**처방**: 검증된 각 `cli_version`이 **정확한 파서/추출기와 수용 위상 하나**를 지목하게 하고,
세는 출력이 최종 응답보다 **앞선다**는 것을 확인한다. 미지의 버전·순서·위상·필드는
`unverifiable`. 단계 3(배선)은 단계 4(버전·구조 게이트) 없이는 **제품 경로에서 도달 불가**여야
한다 — 코드는 먼저 들어가도 좋으나 opt-in이 열리면 안 된다.
→ 이 항목은 **미측정**이다(§8의 남은 측정 1·4와 같은 자리). 위상 fixture 없이는 파서의
안전성을 주장할 수 없다는 §6의 한정과 같은 이야기다.

⚠ **전제 정정(§11-L5)**: 여기서 말한 "opt-in 뒤"가 기존 `source_observation_catalog_tool`을
뜻한다면 성립하지 않는다 — 그 키는 이미 제품 표면이다. 단계 3은 표현 불가능한 내부 능력에
매달거나 단계 4와 원자적으로 착지해야 한다.

### L3 — "배너 하나"는 **산출물 단위가 아니라 자식 단위**다 (내 M1의 구멍)

§9-M1은 *"CLI 기원 배너가 정확히 하나일 때만 진행"*이라고 썼다. 그런데 하나의 authored
artifact가 **자식을 두 번 띄울 수 있다**: 모델이 JSON 형식을 틀리면 파싱 복구 턴이 돈다.
`authoring-llm-call.ts:308-314`가 그 턴에서 façade를 **의도적으로 버리며**, 주석이 이유를 적는다 —
*"`observation_read_facade`는 ONE launch를 지목하므로, 두 번째 디스패치가 그것을 통과하면 첫
디스패치의 영수증 위에 façade를 재시작해 서빙 집합을 지운다. 그러면 모든 인용이 'never served'로
거부된다 — 옳은 런이 자기 증거 검사에 실패한다."*

즉 **이 함정은 이미 알려져 있었고 코드가 피해 갔는데, 내 재조정 설계가 다시 밟았다.** 복구가
일어난 런은 배너가 둘이므로 M1이 (a) unverifiable로 떨어뜨리거나 (b) 더 나쁘게 **아무것도
서빙하지 않은 복구 전사본에 결속**된다. (b)는 "배달 0"을 만들어 옳은 런을 죽인다.

**처방**: 배너·전사본 결속을 **façade를 들고 있던 그 자식**에 대해 수행한다. 자식별 stderr
버퍼에서 증거를 뜨고, 그 자식의 재조정을 복구 턴 **이전에** 끝내거나 그 자식의 불투명 증거를
`callJsonAuthor` 밖으로 들고 나온다. "정확히 하나"는 **자식 하나에 대한 규칙**으로 다시 쓴다.

> **§13-D2로 뿌리가 닫힌다.** 복구가 결정론 구문 수리가 되면 두 번째 자식이 **존재하지 않으므로**
> "산출물 하나 = 자식 하나"가 복원되고 §9-M1의 배너 규칙이 그대로 성립한다. 위 처방은 **불필요해
> 진다** — 단, 그것을 주장으로 두지 않고 *façade를 실은 디스패치는 산출물당 정확히 1회*를
> 테스트로 못박는다(§6-3).

### L1 — 한쪽만 보면 "기록 실패"가 "배달 없음"으로 둔갑한다

설계는 *"각 방출분이 전사본에 있는가"*만 돈다. 그런데 현 서버는 **응답 바이트가 나간 뒤에**
기록을 커밋한다(`facade-server.ts:114`, `facade.ts:503` 주석: 크래시 창에서 **덜 기록되는 쪽**으로
깨지도록 일부러 그렇게 했다). 따라서 **배달은 됐는데 우리 기록에 없는** 방출분이 존재할 수 있다.
단방향 루프는 그것을 못 본 채 "대응 실패 없음 → verified"로 통과하고, **"확인했고 배달 0"**이라는
거짓 진술을 남긴다.

**처방**: 대응을 **양방향**으로 요구한다 — 전사본 쪽에 우리 서버에서 온 결과가 있는데 대응하는
기록된 방출분이 없으면 그 런은 `verified`가 아니라 **`unverifiable`**이다. 개수·순서 또는 도구
호출 id로 일대일을 확인한다. §9-F1이 "짝짓기를 없앤다"고 한 것은 **어느 방출분이 어느 출력에
대응하는가**를 없앤 것이지, **양쪽 총량이 맞는가**까지 버린다는 뜻이 아니다 — 이 구분을 명시한다.

### L2 — 마커를 원자적으로 쓰는 것과 배타적으로 차지하는 것은 다르다

§10-R2-2는 "런치 결속 표식을 원자적으로 먼저 생성"이라고만 썼다. 현 코드는
**check-then-mint-then-write**다(`facade.ts:452-462`에서 영수증 존재를 확인하고, 그 뒤 grant를
mint하고, 그 뒤 기록). 두 프로세스가 **둘 다 부재를 확인**하고 각자 예산을 발급한 뒤 쓰기를
경쟁할 수 있다. 게다가 발행이 `${receiptPath}.tmp`라는 **공유 이름**을 쓴다(`611-613`) — 동시 두
프로세스가 같은 임시 파일을 밟는다.

**처방**: 시작 권리를 `O_CREAT|O_EXCL`로 **mint 이전에** 잡는다(생성 성공이 곧 권리). 임시 파일은
고유 이름 + fsync + rename. **"지우고 시작"을 동시성 제어로 쓰지 않는다** — 그것은 재개용
선행조건 제거이지 배타 획득이 아니다.

### L5 — §10-R2-1의 전제가 틀렸다

R2-1에 *"단계 3은 opt-in 뒤, 단 단계 4 없이는 제품 경로 도달 불가"*라고 적었다. **그 opt-in으로는
성립하지 않는다.** `source_observation_catalog_tool`은 설정에서 수용되고(`settings-chain.ts:568`)
Core API가 읽어(`reconstruct-api.ts:1244`) 작성자까지 흐르며 재사용 키에도 들어 있다. 즉 **이미
제품 표면이다.** 여기에 단계 3을 매달면 사용자가 그 키를 켜는 순간 단계 4 없이 재조정이 돈다.

**처방**: 단계 3을 **표현 불가능한 내부 능력**(설정·API·MCP 어디로도 입력할 수 없는 것)에 매달거나,
단계 3과 4를 **원자적으로 함께** 착지시킨다. `default-off`는 `unreachable`이 아니다.

> **결정됨(§13-D3): 후자 — 3·4 원자 착지.** 설정 키를 받아들이는 커밋과 게이트 커밋을 가르지
> 않는다(§6-2 · §6-7).

### L4 — 재사용은 영수증을 보지 않는다

`writeFreshAuthoredYamlDocument`의 재사용은 **입력 해시 일치**로 결정된다. 이전 시도가 재조정에
성공해 원장을 남기고 이후 단계에서 실패했다면, 다음 런은 그 원장을 **영수증 확인 없이** 재사용할
수 있다. 다행히 자리는 이미 있다 — `authored-artifact-reuse.ts:383-392`에 *"What the AUTHOR will
accept from the model, versioned — and present ONLY under the opt-in whose acceptance rule it
versions"* 필드가 있다.

**처방**: 영수증 참조·해시, attempt/launch id를 재사용 provenance에 싣고, **수용 규칙이
`served`에서 `delivered`로 바뀌는 이번 변경에서 그 계약 버전을 회전**시킨다. 회전하지 않으면 옛
규칙으로 만든 원장이 새 규칙 아래에서 조용히 재사용된다.

### L7 — `unverifiable`은 지금 API 모양으로는 전달되지 않는다

`observationIdsServed(null)`은 빈 집합을 돌려주고, 주석이 *"그것이 소비자를 fail-closed로 만든다"*고
적는다(`facade.ts:836`). 지금은 "영수증 없음"과 "확인했고 배달 0"이 소비자에게 **같은 값**이다.
§9-M2가 요구한 구분은 이 통로를 그대로 두면 **API 모양에서 소멸한다.**

**처방**: `verified(delivered)` / `unverifiable(reason)`을 **판별 가능한 결과형**으로 노출하고,
후자에서 빈 집합으로의 암묵 강등을 **타입 수준에서 불가능**하게 만든다. 인용 거부라는 결과는
같고, 진단과 운영 표면에서만 갈린다(§10-R2-4와 같은 처방의 API 쪽 절반).

### L6 — 실코드 확인 완료: 이 설계는 **복구 불가 창을 넓힌다**

두 킬 지점의 처지가 다르다는 지적을 확인했다.

- **워커만 죽을 때**: 살아남은 런타임이 실패로 표시하고 락을 놓는다. `run.ts:4955`의 catch 주석이
  그 목적을 명시한다 — *"mark the attempt failed like any other error (so run-control is not left
  with a stuck 'running' attempt / held lock)"*. 복구 가능하다.
- **런타임이 워커 종료 후 죽을 때**: 실패 표시를 할 주체가 없으므로 시도가 `running` + 세션 락
  보유로 남는다. 그리고 재개가 그것을 거부한다(`run-control-validation.ts:954-968`):
  `sourceAttempt.attempt_status === "running"` 이거나 held 락이 있으면
  **`"cannot resume a live reconstruct attempt; lease expiry is not takeover authority"`**.

마지막 문장이 처방을 결정한다. **리스 만료가 인수 권한이 아니라는 것은 의도된 불변식**이므로
"타임아웃 후 자동 인수"는 이 저장소에서 답이 아니다. 그것을 도입하면 run-control이 지키는 성질을
배달 재조정 편의를 위해 깎는 것이 된다.

**이 설계가 문제를 키운다.** 재조정은 정의상 **워커 종료 후 런타임에서** 돈다 — 즉 위의 두 번째
킬 지점 **한가운데**다. 지금은 그 구간이 짧지만(마무리·기록), 재조정이 들어오면 전사본 특정 ·
구조 검증 · 파싱 · 대응 검사 · 영수증 발행이 모두 그 안으로 들어온다. **복구 불가 창이 눈에 띄게
넓어진다.**

**처방(둘 중 하나를 명시적으로 고른다)**:
1. **명시적 복구 행위**를 만든다 — 버려진 그 디스패치를 지목해 재조정하거나(전사본은 여전히
   디스크에 있다), 재조정 불가로 판정해 `unverifiable`로 닫고 새 시도를 연다. 인수가 아니라
   **한 시도의 종결**이므로 위 불변식과 충돌하지 않는다.
2. 만들지 않는다면, **"이 킬 지점은 새 세션 루트가 필요하다"를 문서화**하고 재조정이 그 창을
   넓힌다는 사실을 함께 적는다.

어느 쪽이든 **선택은 owner의 것**이다. 1이 사용자 경험상 낫지만 run-control에 새 행위를 추가하는
일이므로 이 설계의 범위를 넘는다.

> **결정됨(§13-D1): 2 — 문서화만.** 명시적 복구 행위는 만들지 않는다. 대신 단계 4 라이브에서
> **창 폭을 실측해 기록**한다 — 수치가 예상을 벗어나면 이 항목은 재개된다.

## 12. R3 교차검증 반영 — 조용한 오답 (2026-07-28)

R3의 두 번째 관점: *"완주하고 영수증까지 쓰면서 **조용히 틀리는** 경로는 어디인가."* 패킷
[16](16-crossverify-packet-silent-wrongness.md), 판정 [19](19-review-gpt-5.6-sol-silent-wrongness.md).
VERDICT = **조용한 오답 경로가 살아남는다** — BLOCKER 2 + MATERIAL 3.

> 이 렌즈는 provider capacity로 **4회 NOT-RUN 후 5번째에 반환**됐다. 거절은 전부 추론 전이라
> 내용과 무관하고 토큰 소모가 없다. §11의 계상("이 축은 아직 아무도 보지 않았다")은 이 절로
> **해소된다.**

|---|---|---|---|---|
| S1 | **복구 턴이 다른 시도의 배달 권위를 물려받는다** | BLOCKER | ✅ 테스트 픽스처까지 확인 | 복구를 결정론 수리로 제한하거나 재작성 |

### S1 — 관찰을 한 번도 못 받은 워커가 쓴 주장에 배달 영수증이 찍힌다 (기존 코드의 결함)

시퀀스: 1차 워커가 관찰 `O`를 fetch했고 재조정은 `O`가 **그 워커에게** 도달했음을 옳게 증명한다.
그런데 1차 출력의 JSON이 깨지면 `callJsonAuthor`가 **2차 디스패치**를 돌리고 façade를 뗀다 —
2차 워커는 깨진 텍스트와 파싱 오류만 받을 뿐 **`O`의 본문을 받지 못한다.** 2차가 `O`의 id를
유지한 채 주장을 바꾸거나 지어내면, 소비자는 **1차의 영수증**으로 그 인용을 승인한다.

아티팩트는 이렇게 남는다: 1차 `malformed_json` · 복구 `succeeded` · 영수증 `delivered=[O]` ·
원장이 `O`를 인용 · 검증 `valid`. **받아들여진 의미 스칼라가 `O`를 못 받은 워커에게서 왔다는
사실은 어디에도 없다.**

**실코드 확인 — 이건 이미 테스트가 승인하고 있다.** `observation-read-pull.test.ts:376-448`의
픽스처에서 1차 응답은 문자 그대로 `"{ not json"`(내용 전무)이고, 2차 응답은 **완결된 evidence
cluster를 통째로 생성**한다(`proposed_answer_summary: "The fetched observations converge."`,
`evidence_observation_ids: fetched`). 테스트는 그것을 **성공으로 단언**한다. 같은 테스트의 주석은
*"워커는 실제로 fetch했다. 복구는 JSON을 재포맷할 뿐이다"*라고 전제하는데, **그 픽스처가 전제를
반증한다** — 재포맷이 아니라 의미 생성이다. 복구 프롬프트가 구두점 수준의 수정을 요구하더라도
**런타임이 그것을 강제하지 않는다.**

**처방(둘 중 하나)**: (a) 복구를 **결정론적 구문 수리**로 바꾸고 모든 스칼라·문자열·id가
불변임을 증명한다, 또는 (b) 새 grant로 작성을 다시 돌리고 최종 아티팩트를 **그 최종 시도의
영수증**에 결속한다. 스칼라를 더하거나 바꾸는 복구가 다른 시도의 배달 권위를 물려받아서는 안 된다.
→ §11-L3과 같은 뿌리(복구 턴은 별개의 자식)이지만 **다른 피해**다. L3은 재조정이 엉뚱한 전사본에
결속되는 문제였고, S1은 재조정이 **옳게** 결속돼도 그 영수증이 **다른 워커의 산출물**을 인증하는
문제다. 둘 다 닫아야 한다.

> **결정됨(§13-D2): (a) — 결정론적 구문 수리.** 2차 LLM 디스패치를 제거한다. 뿌리가 같으므로
> **L3도 이 경로에서 함께 닫힌다.** 착지는 **단계 A**(§6-3) — 재조정보다 먼저다.

### S2 — 개명은 이름을 바꾸는 일이 아니라 **표면을 닫는 일**이다

`served=[O]`(전송 사실)와 `delivered=[]`(중간이 잘려 미도달)가 갈리는 런에서, 소비자나 재개
경로가 **하나라도** `served`에 남아 있으면 `O`가 승인된다. 원장 검증에는 배달 영수증 입력이
없으므로 원장과 그 검증이 **둘 다 성공**이라고 말하고, 어떤 운영 투영도 모순을 드러내지 않는다.

**실코드 확인**: `AUTHORED_OUTPUT_CONTRACT_VERSION = 2`이고 그 주석이 규칙을 못박는다 —
*"authored artifact의 ACCEPTANCE 규칙이 입력 변화 없이 바뀔 때 올린다."* `served`→`delivered`가
정확히 그 경우다. 올리지 않으면 **옛 규칙으로 만든 원장이 새 규칙 아래에서 조용히 재사용된다.**

**처방**: 전송/배달을 **브랜드 타입으로 분리**하고 `observationIdsServed`를 소비자 사정권에서
제거한다. 정본 검증이 `인용 id ⊆ delivered id`를 **직접 단언**하게 한다. 영수증 참조·해시와
작성 시도를 영속하고, 계약 버전을 올리며, `served`만 있는 옛 아티팩트는 거부하거나 재생성한다.
리뷰어가 짚은 이행 좌석(§Q3): 영수증 리더·`observationIdsServed`·`writeAnswerSupportLedger`·
세션 2차 기동 검사·라이브 probe 스크립트·두 테스트 파일·원장 검증·계약 버전.

### S3 — "확인했고 배달 0"은 대개 **거짓 진술**이다

모델이 쓰는 JS가 봉투를 파싱해 본문만 출력하면(`text(page.entries[0].body)`) **관찰은 온전히
도달했는데** 서버의 정본 문자열은 전사본에 없다. 재조정은 구조적으로 성공하고 `delivered=[]`를
발행하며 인용은 거부된다. 아티팩트는 *"확인했고 아무것도 배달되지 않음"*이라고 말하지만, 실제로
확인된 것은 *"서버의 정본 렌더링을 그대로 찾지 못함"*뿐이다. **아무도 못 알아챈다 — 전사본 리더는
명세대로 동작했고, 미대응 렌더링을 분류하는 자리가 없기 때문이다.**

**처방**: 정본 그대로 통과하는 렌더링을 구조적으로 강제하거나, 부정 상태의 이름을
**`verbatim_delivery_not_attested`**(정본 그대로는 확인되지 않음)로 바꾼다. 방출분별 대응 처분을
기록한다. **미대응을 "내용이 없었다"의 증거로 보고하지 않는다.**
→ §9-F4가 "미지의 렌더링은 거짓 음성만 만든다"고 적은 것은 **판정 안전성**의 진술로는 옳지만,
그 거짓 음성을 **사실 진술로 기록**하는 순간 틀린다. 안전한 것과 참인 것은 다르다.

### S4 — 서버의 기록 순서는 모델이 본 순서가 아니다

서버는 요청을 직렬화하고 stdout 쓰기 성공 후 커밋하므로 **와이어 순서**는 실재한다. 그러나
모델이 쓰는 JS는 그것을 구속하지 않는다 — `Promise.all([read(A), read(B)])` 뒤에 `text(b)`,
`text(a)` 순으로 출력하면 서버는 `A,B`로 기록하고 모델은 `B,A`로 받는다. 리듀서가
`part_allowance`에서 리셋하므로 **재생 순서가 다르면 다른 파티션이 선택**돼 이미 완전했던 배달을
거짓으로 거부할 수 있다. (미도달분을 인정하는 방향으로는 여전히 깨지지 않는다.)

**처방**: 재생 순서를 전사본 페이로드 순서 + 대응 위치에서 유도하고 모호하면 fail-closed, 또는
더 낫게 **누적을 순서 비의존으로** 만든다 — `(observation_id, hash, part_allowance)` 파티션을 모두
추적하고 **그중 하나라도 완전하면 인정**한다. 후자는 §9-F2의 "규칙을 재유도하지 않는다"와
충돌하지 않는다(같은 규칙을 순서 비의존 형태로 적용할 뿐이다).
→ 두 실행이 모두 `exec`당 MCP 호출 1회 위상이라 **이 차이를 드러낼 수 없다**(§9-M4와 같은 구멍).

> **채택: 후자(순서 비의존 누적) — 단계 0b**(§6-4). 실코드 확인으로 두 가지가 더 붙었다.
> ① 순서 의존은 재조정만의 문제가 아니라 **이미 실행 중 경로에 있다**(같은 페이지 집합이 도착
> 순서에 따라 다르게 판정된다). ② 순서 비의존 형태는 방어 성질을 **잃지 않는다** — 주석이 근거로
> 드는 293자 구멍 사례는 파티션이 갈리므로 여전히 거부된다.

### 수렴 — 주 세션의 검산과 독립적으로 일치한 지점

리뷰어의 Q1 답: `A1(도달)·B1(미도달)·A2(도달)`에서 전체 재생은 `A:{2}`로 끝나지만 배달분만
재생하면 `A:{1,2}`가 되어 **인정된다. 그리고 그 인정은 옳다** — 한 파티션의 두 파트가 실제로
모델에 도달했기 때문이다. *"필터된 재생은 파트를 발명할 수 없다; 고유 오차는 잘못된 인정이 아니라
보수적 거부다."* 이는 §9-F2 검토 때 주 세션이 스스로 도출한 결론과 **같다**. 서로 모르는 두 경로가
같은 곳에 도달했으므로 이 항목의 신뢰도는 높다.

## 13. owner 결정 (2026-07-28)

§11·§12가 주 세션 임의로 정하면 안 되는 갈림길 3건을 남겼다. owner가 아래로 확정했다.
§6의 단계 계획은 이 결정들 위에 서 있다.

### D1 · 호스트가 재조정 도중 죽었을 때 (§11-L6) → **② 문서화만**

명시적 복구 행위를 **만들지 않는다.** 런타임이 워커 종료 후 죽으면 시도는 `running` + 세션 락
보유로 남고 재개가 거부한다(`run-control-validation.ts:954-968`,
*"lease expiry is not takeover authority"*). 그 킬 지점은 **새 세션 루트가 필요하다.**

근거: 자동 인수는 run-control이 지키는 불변식을 배달 재조정 편의로 깎는 일이고(§11-L6), 명시적
종결 행위는 run-control에 새 행위를 더하는 일이라 이 설계의 범위를 넘는다. 재조정이 넓히는 창은
파일 읽기 + JSONL 파싱 + 영수증 발행이라 초 단위 이하일 가능성이 높으나 **미측정**이다.

→ 이 결정을 검증 가능하게 유지하는 조건: **단계 4 라이브 N=1에서 그 구간의 실측 소요를
기록한다.** 수치가 예상을 크게 벗어나면 D1은 재개된다. 명시적 복구 행위는 백로그.

### D2 · 복구 턴이 다른 시도의 배달 권위를 물려받는 문제 (§12-S1) → **(a) 결정론적 구문 수리**

LLM 복구 디스패치를 제거하고 결정론적 수리로 바꾼다. 상세는 §6-3.

근거: (b)(새 grant로 재작성 후 최종 시도 영수증에 결속)는 같은 결함을 **감시로** 막는 모양이고
디스패치·예산이 늘어난다. (a)는 **클래스를 구조적으로 제거**한다 — 지어낼 수 있는 자식이
아예 없으면 지어낸 것을 인증할 일도 없다. 대가는 지금 LLM 복구가 살려내던 런 일부(특히 절단)가
실패로 떨어지는 것이며, owner가 그 비용을 수용했다.

→ 부수 효과로 §11-L3(복구 턴이 두 번째 자식)의 뿌리가 같은 경로에서 닫힌다. **주장이 아니라
게이트로 확인한다**(§6-3).

### D3 · 단계 3의 도달성 (§10-R2-1 · §11-L5) → **② 단계 3·4 원자 착지**

표현 불가능한 내부 능력에 매다는 길(①)을 택하지 않는다. 그것은 나중에 떼어낼 은폐 개념을 하나
더 만든다. 대신 **설정 키를 받아들이는 커밋과 버전·구조 게이트 커밋을 가르지 않는다.**

근거: `source_observation_catalog_tool`은 이미 제품 표면이므로(`settings-chain.ts:568` →
`reconstruct-api.ts:1244`) 거기에 매달면 사용자가 키를 켜는 순간 게이트 없이 재조정이 돈다(§11-L5).
`default-off`는 `unreachable`이 아니다.
