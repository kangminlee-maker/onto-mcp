# 타당성 검토 — 절단을 사후 탐지하는 대신 애초에 일으키지 않는다 (2026-07-30)

> **상태**: 타당성 검토. owner 지시로 개설. 설계가 아니라 **가능한가**에 답하는 문서다.
> **계기**: owner 질문 — *"모델 입력 한도를 고려해서 serve할 게 아니라, artifact로 만들고 주소를
> 줘버리면 되지 않나?"* 그 방식 자체는 §1에서 기각되지만, 질문이 **아무도 안 건드린 축**을 드러냈다.

## 0. 왜 이 문서가 생겼나

이 트랙 전체가 **절단을 사후에 탐지**하는 데 쓰였다. `served` → `delivered` 권위 이동, rollout
리더, 재조정기, 그리고 그것을 지키는 버전 핀과 그 핀을 대체할 프로브(`21-…md`, 현재 파킹).

그동안 **"애초에 절단이 안 나게 한다"는 축은 한 번도 검토되지 않았다.** 절단이 드물어지면
`delivered`와 `served`가 대부분 일치하고, 재조정은 **드문 예외를 잡는 안전망**으로 내려간다.
그러면 프로브가 짊어진 부담도 함께 내려간다.

## 1. owner가 제안한 형태(주소 건네기)는 기각 — 두 가지 이유

**① 워커에게 파일 접근이 없다. 의도적으로.**

프로덕션 디스패치는 `--disable shell_tool`을 건다(`llm-caller.ts`). 주석이 이유를 적어 두었다:

> MCP 표면만 닫는 것으로는 부족하다 — 워커가 **운영자 자격증명으로 `gh`/`git`에 셸 아웃**할 수
> 있고, 그건 다른 문으로 들어온 같은 권한이다.

그리고 그 근본 이유:

> **신뢰할 수 없는 소스 텍스트를 먹는 것이 이 제품의 정상 동작**이다 — 분석 대상에 심긴 지시가
> 행동할 수 있는 모델에 도달한다.

façade가 존재하는 이유가 바로 그것이다. 주소를 주려면 그 문을 다시 열어야 한다.

**② 열어도 안 풀린다.** 절단은 전송 방식이 아니라 **exec 출력 총량**에 걸린다. 파일을 `cat`해도
같은 예산을 먹는다. 도움이 되려면 **작게 나눠 읽어야** 하는데, 그건 지금 커서 페이지네이션이
이미 하는 일이다.

## 2. 그럼에도 질문이 옳았던 지점 — 실제 원인은 "크기"가 아니라 "한 exec에 몰림"

실측된 세션을 다시 보면:

```
한 exec 안에서 4회 호출:  2,015 + 8,001 + 32,035 + 128,007 = 170,058자
천장 ≈40,150자 → 앞의 둘만 도달
```

**32,035자짜리는 천장보다 작은데도 못 갔다.** 앞의 것들과 **같은 exec 출력 예산을 나눠 썼기**
때문이다. 즉 페이지를 작게 만드는 것만으로는 안 되고, **한 exec이 만드는 출력 총량**이 관건이다.

그리고 그 횟수는 **모델이 정한다.** 런타임은 지금 그것에 대해 아무 말도 하지 않는다.

## 3. 확립된 역량 — 이 트랙이 이미 측정해 둔 것

|---|---|---|
| `tool_output_token_limit`은 **실재하고 선언하면 지켜진다**(2000 선언 → 60,000자 결과 절단) | `10-…md` §1-③ | 런타임이 천장을 **선언**할 수 있다. 단 **내릴 수만** 있다(`05` §2) |
| **ack 왕복이 바이트 정확하게 동작**한다 — 결과에 실린 값을 워커가 다음 호출 인자로 되돌린다. 128비트 challenge 4/4 EXACT | `10-…md` §1-① | 런타임이 **수신을 확인하고 다음을 서빙**하는 프로토콜이 가능하다 |
| 정직한 워커의 복사 실패 **0건**(약한 모델·낮은 effort) | `10-…md` §1-② | ack 비용이 우려보다 작다. 단 N=4, **하한으로 읽어야** 한다 |
| `structuredContent`는 **천장을 먹지 않는다** — 150KB를 달아도 텍스트 5/5 도달 | `09-…md` §1 M-B | 절단을 지배하는 것은 `content[0].text` **하나뿐** |

## 4. 아직 안 풀린 것 둘 — 설계 전에 닫아야 한다

### 4-1. 절단이 비결정적으로 보인다 (`10-…md` §2)

동일 설정·동일 크기에서 두 하니스가 **반대 결과**를 냈다(60,000자 절단 / 60,053자 무손실).

> **가설(미검증)**: 두 하니스가 **모델에게 시킨 일이 다르다.** 절단 하니스는 페이로드를 통째로
> 보고하게 했고, ack 하니스는 **증인 몇 개만** 돌려보내게 했다. 그렇다면 이건 비결정성이 아니라
> **"모델이 출력에 무엇을 싣느냐"의 차이**이며, 이 검토의 핵심 축과 정확히 같은 축이다.
>
> 닫는 법: 두 하니스의 exec 출력 크기를 실 전사본에서 직접 비교한다. 증거는 이미 디스크에 있다
> (`development-records/benchmark/ack-roundtrip/`·`tool-result-truncation/`). **새 디스패치가 필요 없다.**

### 4-2. MCP 결과가 컨텍스트에 **자동으로** 들어가는가 — 이것이 전부를 가른다

`09-…md`는 *"모델은 `content[0].text`만 본다"*로 읽힌다. 그런데 레코드 종류를 보면 다르게 읽힌다:

- `mcp_tool_call_end`는 **`event_msg`** — 대화 항목이 아니다
- `custom_tool_call_output`은 **`response_item`** — 대화 항목이다
- MCP 호출은 **exec 안에서** 일어난다(실 전사본: 한 `custom_tool_call` 아래 `mcp_tool_call_end` 4건)

이 배치가 맞다면 **MCP 결과는 exec의 JS 런타임에 도착할 뿐이고, 모델 컨텍스트에는 exec이 출력한
것만 들어간다.** 즉 `09`의 5/5는 "codex가 자동 주입한다"가 아니라 "워커의 exec 코드가 그 필드를
읽어 출력했다"일 수 있다.

**이 구분이 왜 전부인가:**

| 가정 | 절단 방지의 지렛대 | 재조정의 의미 |
|---|---|---|
| 자동 주입된다 | 런타임의 페이지 크기·천장 선언 | 지금 그대로 |
| **exec 출력만 들어간다** | **모델의 출력 습관** — 프롬프트가 지렛대가 된다 | "서빙"과 "도달" 사이에 **모델의 선택**이 하나 더 있다 |

> **이건 추론이지 측정이 아니다.** `09`의 프로브가 워커에게 무엇을 시켰는지 확인하면 닫힌다
> (`scripts/probe-mcp-result-field-authority.mts`). 역시 **새 디스패치가 필요 없다.**

## 5. 만약 4-2가 "exec 출력만"으로 확정되면 — 가능한 지렛대

전부 지금 구조 안에서 되고, 보안 자세를 건드리지 않는다.

1. **페이지 예산을 천장 한참 아래로.** 필요조건이지 충분조건은 아니다(§2).
2. **exec당 1회 호출 유도.** 프롬프트가 "하나 꺼내고 그 결과를 출력한 뒤 다음을 꺼내라"고 지시한다.
   강제는 아니지만 가장 값싸다.
3. **누적 인지 서빙.** façade가 이 디스패치에서 내보낸 누적 바이트를 이미 안다(grant의 누적 예산).
   천장 근처에 다다르면 **페이지 안에 경고를 실어** 보낸다 — "지금까지 N자를 받았다. 더 요청하기
   전에 출력하라."
4. **ack 게이팅.** 다음 페이지를 서빙하기 전에 이전 페이지의 challenge를 요구한다(§3에서 실측됨).
   가장 강하지만 가장 비싸고, **주의**: ack는 "exec 런타임이 받았다"를 증명할 뿐 "모델이 읽었다"를
   증명하지 않는다 — JS가 값을 뽑아 되돌릴 수 있기 때문이다. 재조정을 대체하지 못한다.

## 6. 이것이 없애는 것과 없애지 못하는 것

**없앤다**: 절단의 빈도. `delivered`와 `served`가 대부분 일치하게 되어, 재조정이 **상시 판정**에서
**드문 예외 탐지**로 내려간다. 그러면 파킹된 프로브(`21-…md`)가 짊어진 부담도 함께 내려간다 —
인증이 없을 때 잃는 것이 작아지기 때문이다.

**없애지 못한다**: 재조정 자체. 절단을 줄여도 **0이 되지는 않고**, "서빙했다 ≠ 도달했다"는
구조적 사실은 남는다. 그리고 §5-4의 주의대로 ack도 그 간극을 못 메운다.

## 7. 타당성 판정

**추가 실측 2건으로 닫히고, 둘 다 새 디스패치가 필요 없다**(§4-1 · §4-2). 디스크의 기존 증거를
다시 읽으면 된다.

그 둘이 닫히기 전에는 §5의 지렛대 중 무엇이 실제로 듣는지 알 수 없으므로, **설계로 넘어가지
않는다.** 특히 4-2가 "자동 주입"으로 나오면 §5-2·§5-3이 통째로 무효다.

## 11. 방향 전환 — 크기 견고성 (owner 지시 2026-07-30)

§8의 상수 충돌을 보고 owner가 물었다: *"크기에 robust한 설계가 필요하다. 어떤 구조적 변화면
엄청나게 큰 내용도 작은 내용도 대응 가능한가?"* 상수 조합이 아니라 **구조**를 바꾸기로 한다.

### 11-1. 경직성의 뿌리 — 배달의 단위가 "관찰 전체"다

```
단위 = 관찰 전체
  → 모든 파트가 도달해야 함 (coversWholeObservation)
  → 파트 수가 크기에 비례
  → 호출 상한 32 · exec 천장과 충돌
```

크기 의존성이 전부 여기서 나온다. 단위가 "전체"인 한, 어떤 상수 조합으로도 큰 내용은 벽을 만난다.

### 11-2. 구조 변경 — 단위를 구간(span)으로 내린다

| | 지금 | 제안 |
|---|---|---|
| 배달 판정 단위 | 관찰 전체 | **구간** |
| 인용 | "관찰 X" | "관찰 X의 이 구간" |
| 큰 관찰 | 영구 인용 불가 | 읽은 구간만 인용 |
| 작은 관찰 | 그대로 | 그대로(구간 1개 = 전체) |

**같은 메커니즘이 양쪽을 처리한다.** 800 KB짜리는 구간이 많이 나올 뿐, 500자짜리는 구간 하나다.
특수 케이스가 없다.

부수로 **증거가 더 강해진다**: 800 KB 관찰 전체를 인용하는 것은 사실상 아무것도 말하지 않는다.
"이 부분을 읽었고 그것이 뒷받침한다"가 더 정확한 증거다.

### 11-3. 재료가 이미 있다 — 실코드 확인

`observation-read.ts`가 구간을 정의할 모든 것을 이미 갖고 있다:

- `body` = 관찰 레코드의 **정규 직렬화 문자열**
- `observation_content_sha256`이 **정확히 그 문자열**을 덮는다
- 파트는 **그 문자열의 슬라이스**다 — *"concatenating an observation's parts in order reproduces it
  character-for-character"*
- `part_allowance`가 **분해의 identity**다

따라서 구간은 `body`의 **문자 범위**로 정확히 지칭 가능하다.

> **정정(2026-07-30, 교차검증이 반박)**: 여기 처음에 *"범위는 `(part_index, part_allowance)`에서
> **산술로 도출된다. 새 계산이 없다**"*고 적었는데 **거짓이다.** `splitBodyByJsonCost`는 문자 수가
> 아니라 **JSON 이스케이프 비용**으로 자르고, `codePointJsonCost`가 비균일하다(`"`·`\`·일부 제어문자
> = 2, `< 0x20`·surrogate = 6, 그 외 1). 게다가 allowance 자체가 요청의 id 목록에 따라 달라진다.
> → 파트 경계는 내용 의존적이며, **런타임이 오프셋을 명시적으로 실어 보내야 한다.** 페이지 계약
> 변경이지 공짜가 아니다.

### 11-4. 함정 — 구간을 `part_index`로 지칭하면 안 된다

파트 경계는 **페이지 예산이 만든 전송 아티팩트**다. 예산이 바뀌면 "파트 17"이 다른 내용이 되어
인용이 불안정해진다. 코드가 이미 경고한다 — *"두 요청이 같은 count로 다른 경계를 만들고, 인덱스를
병합하면 가운데 구멍이 있는 '완전' 커버리지가 됐다(측정됨)"*.

→ **`(observation_id, content_sha256, [start, end))`** 로 지칭한다. 예산 무관하게 안정적이다.

### 11-5. owner 결정 — 부분 읽기·전체 주장은 **구조로 막지 않는다**

구간 인용을 허용하면 "일부만 읽고 전체에 대해 주장"이 가능해진다. 지금은 전체 도달 요구가 그것을
우회적으로 막고 있었다.

> **owner 판단(2026-07-30)**: *"관찰의 일부만 읽고 전체에 대해 주장했다면 논리 검증에서 막힌다.
> 구조적으로 막을 필요는 없다."*

즉 **인용의 범위가 정직한지는 배달 층의 문제가 아니라 주장-증거 정합성의 문제**이며, 이미 별도
판정이 다룬다. 배달 층은 "이 바이트가 도달했는가"만 답한다. **층의 책임이 오히려 깨끗해진다.**

### 11-6. 따라오는 것

- **호출 상한 32**가 정확성 제약에서 **비용 제약**으로 내려간다 — 모든 파트를 받을 필요가 없다
- **페이지 예산 인하**는 여전히 필요하다(각 페이지가 한 exec 출력에 담겨야 한다). 다만
  **전부-아니면-전무 절벽이 사라진다**
- **exec당 1회 유도**는 그대로 필요하고, 이것은 강제가 아니라 **요청**이다(프롬프트 지렛대)

### 11-7. 교차검증이 정정한 것 (`gpt-5.6-sol`/max, 2026-07-30)

같은 눈가림 패킷으로 독립 초안을 받아 대조했다. **구조는 독립적으로 수렴했다**(단위를 구간으로).
정정된 것 둘은 전부 주 세션 쪽 오류다.

1. **오프셋 산술 도출은 거짓** — §11-3의 정정 상자 참조. 실코드 확인 완료.
2. **코퍼스 수치가 부정확했다.** 주 세션이 Python `json.dumps(ensure_ascii=False)`로 쟀는데
   프로덕션은 `JSON.stringify`다. 이스케이프가 달라 어긋났다. 게다가 **fixture의 `PROVENANCE.md`가
   정확한 값을 이미 못박아 두고 있었다**(최대 780,114 · 전체 정규 JSON 2,710,411) — 커밋된 값을
   안 보고 다시 잰 것이다.

   이 정정이 판단을 바꾼다: **32,000 예산에서 최대 관찰이 28파트**라 호출 상한 32 **안에 들어온다**
   (주 세션 계산으론 29로 거의 닿았다). 16,000에서는 56파트로 여전히 초과.

**교차검증이 더한 설계 요소 둘** — 채택한다:

- **`range_content_sha256`** — 구간 자체의 해시. 인용이 **자기 검증적**이 된다(구간 내용이 바뀌면
  해시가 안 맞는다). 주 세션 설계엔 없었다.
- **모델에게는 불투명 id만**(`orng_v1_…`) 주고 런타임이 해석한다. 모델이 오프셋을 지어낼 수 없게
  만드는 형태이며, 이 저장소의 "결정론적 값은 LLM 권위 밖" 원칙과 정확히 맞는다.
