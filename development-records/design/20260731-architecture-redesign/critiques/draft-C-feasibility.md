## 종합 판정: major_gap

스택 자체는 대부분 실재하고 성숙하다(TS/Node, ajv, tree-sitter wasm, git+JSONL, vitest 전부 in-house).
유일 신규인 scip-typescript도 실재한다(Sourcegraph 제작, npm 배포, tsc 기반이라 컴파일 가능한
프로젝트 요구 — 현재 유지보수 활발성은 확인 필요). 날조된 부품은 없다.

문제는 부품이 아니라 **접합부의 비용 산정**이다. 하중을 받는 실현성 주장 3개가 그대로는 성립하지
않는다: (1) R5 캐시 무효화 단위가 새로 도입하는 유일한 증거 클래스(전-프로그램 참조 엣지)에 대해
틀렸고, (2) 이행 2단계의 "신규 checker 코드 0"과 Tier-0 "초 단위"가 동시에 성립할 수 없으며(실물
스크립트가 델타 실행 불가), (3) 신규 귀납 norm의 checker 저작 경로가 설계에 없어서 외부 도메인
이론은 사실상 전부 semantic(공시 전용)으로 착지한다 — 커널 재구축이 사는 blocking 강제력이 기존
수작업 checker 범위에 갇힌다는 뜻이다. 전부 수리 가능해 보이나, 수리하면 초안이 광고한 비용
프로파일(즉시성·저비용·"추출기 하나 더")이 눈에 띄게 나빠진다.

## F-1 (high) — 전-프로그램 증거에 대해 캐시 무효화 단위가 틀렸다 (R5의 급소)

§7 증분성 표는 evidence의 캐시 키를 `(source content_sha256, extractor logic_sha256)`,
무효화 단위를 "소스 파일/구간"으로 선언한다. 그러나 §8이 유일 신규로 도입하는 scip-typescript의
산출 — 호출·타입 **참조** 엣지 — 는 파일-지역적 속성이 아니라 전-프로그램 속성이다. 파일 A의
심볼 이름 변경·export 제거는 파일 B, C의 참조 집합을 바꾼다. B와 C의 content_sha256은 불변이므로
파일 단위 키로는 B·C의 참조 증거가 신선한 것으로 남는다.

**실패 시나리오**: `src/core-runtime/x.ts`가 `parseSpan()`의 마지막 호출 사이트를 제거하는
커밋. scip 재인덱스는 x.ts에 대해서만 돌고(파일 키 기준), `parseSpan` 선언 파일의 "참조 ≥1"
증거는 캐시에서 그대로 서빙된다 — sound 라벨을 단 채 이미 거짓이 된 증거. 역방향도 같다:
참조가 새로 생겼는데 stale "참조 0" sound 증거가 남으면, §3.2-3 소비 시효 게이트가 **살아 있는
concept을 자동 retire**한다. 초안이 "근사 엣지 위 부재 추론 금지"로 봉인한 바로 그 부재 오판
클래스가, sound 라벨을 우회로 삼아 재발한다 — 라벨은 추출기의 건전성만 보증하고 캐시의 신선도는
보증하지 않기 때문이다.

**repair**: sound 참조 증거의 캐시 키를 파일 단위가 아니라 컴파일 유닛(tsconfig 프로젝트) 세대
해시로 올려라 — 즉 어떤 소스 변경이든 scip 증거 전량 무효화. self 규모(운영 242파일)에선 재인덱스가
수십 초 수준으로 추정돼 수용 가능하나(실측 필요), 이 수리는 F-2와 합쳐져 "Tier-0 매 run 초 단위"
주장을 공식적으로 철회하게 만든다. §7 표에 evidence class별 무효화 단위 열을 추가해야 한다
(파일-지역 class와 전-프로그램 class는 다른 행이다).

## F-2 (high) — 이행 2단계의 두 주장이 서로를 부정한다: "신규 checker 코드 0" ∧ "Tier-0 델타 backtest 초 단위"

§11 2단계는 "checker_ref는 기존 check-* 스크립트 그대로 결속(신규 checker 코드 0)"이라 하고,
§5.4 Tier-0는 "변경된 증거에 한정한 backtest census 델타"가 "초 단위"로 매 run 돈다고 한다.
실물을 확인했다: `scripts/check-import-boundary.ts`(초안 §2.2가 1일차 결속 예시로 든 바로 그
파일)는 `src/`를 재귀로 전량 걷는 전-repo 스캐너이고, argv/스코프 입력이 없다. `scripts/`의
check-* 14종이 같은 형태다(대상 열거가 스크립트 내부 상수).

**실패 시나리오**: 2단계 가동 첫 주. 매 진화 run의 Tier-0가 admitted checkable norm 전수의
backtest 델타를 돌려야 하는데, 결속된 checker가 델타를 받을 수 없으므로 실제 실행은 "scope가
변경 파일과 교차하는 checker의 전-repo 재실행" = 사실상 현행 CI 가드 스위트 1회다. 분 단위다.
"초 단위"가 되려면 스크립트들에 스코프 입력·증거-질의 인터페이스를 이식해야 하고 그 순간
"신규 checker 코드 0"이 깨진다 — 그리고 이식된 스크립트는 negativeControl 변이 결속(§3.3)을
새로 통과해야 하므로 변이 fixture 저작 비용이 스크립트 수만큼 붙는다.

**repair**: 2단계 주장을 정직하게 분리하라 — "1일차 결속은 전-repo 실행(분 단위, 현행 CI 비용과
동일)이고, 델타-capable checker로의 이식은 별도 비용 항목(스크립트당 이식+변이 fixture)"으로.
Tier-0의 '초 단위'는 (a) binding 해시 재검증에만 붙이고 (b) backtest 델타는 이식 완료 checker에
한정해 점진 달성으로 재기술. 수리 가능하나 이행 일정과 비용표를 다시 써야 한다.

## F-3 (high) — 신규 귀납 norm의 checker 저작 파이프라인이 없다 → 외부 도메인에서 커널의 구매력 붕괴

초안 전체에서 checker의 출처는 두 가지뿐이다: 기존 check-* 스크립트 결속(2단계), 그리고 침묵.
§3.1[3]에서 LLM이 norm 후보를 저작하지만, realization=checkable이 되려면 checker_ref+sha256이
실파일로 결속되어야 한다(§2.2 L2 메타규범). **새로 귀납된 norm의 checker 코드는 누가 쓰는가?**
LLM이 쓴다면 — LLM 저작 코드를 커널이 실행하는 경로(샌드박싱·checker 품질 검증·negativeControl
fixture 저작)가 설계에 전혀 없다. 사람이 쓴다면 — "승격·유지·판정·귀납은 사람 0"(§5.3)과
충돌한다. 초안의 §3.1[4] "checker(있으면)"라는 괄호가 이 구멍의 자백이다: checker가 없는 norm은
semantic으로 착지하고, semantic은 공시 전용이다(§4.3).

**실패 시나리오**: 6단계, 외부 코퍼스(예: 타 언어 서비스 repo) reconstruct. 귀납이 norm 40개를
수용시킨다 — 전부 semantic(그 코퍼스엔 결속할 기존 check-* 스크립트가 없으므로). review v2가
이 도메인에 대해 내는 것 = LLM 렌즈 finding + 결정론 수용 게이트 = **현행 review 파이프라인과
기능적으로 거의 동일한 산출**. 커널·원장·census·fixedpoint 전체 재구축 비용을 치르고 산 blocking
강제력이 self 도메인의 기존 수작업 checker 밖으로 한 발도 못 나간다. R1의 노이즈 정의("검사
가능한 귀결이 없으면 노이즈")와도 자기충돌한다 — 외부 도메인의 admitted norm 대부분이 자기
정의상 노이즈 후보다.

**repair**: 고칠 수는 있으나 방법이 설계의 미답 영역이다: (a) LLM checker 저작 + 커널 샌드박스
실행 + 변이 결속을 신규 파이프라인으로 설계에 추가(상당한 신규 표면 — 커널 ≤3k줄과 정면 충돌)
하거나, (b) checker를 자유 코드가 아니라 커널 combinator 위의 선언적 predicate DSL로 제한해
LLM이 "코드"가 아니라 "스키마 검증되는 선언"을 제출하게 하거나(표현력 손실), (c) 외부 도메인은
공시 전용임을 테제 수준에서 인정하고 비용 정당화를 self 한정으로 다시 쓰거나. 셋 중 무엇도
현재 초안에 없다.

## F-4 (high) — 소비 시효 게이트가 외부 코드 도메인에서 작동 불능이거나, 언어당 SCIP 부채가 숨어 있다

§3.2-3 소비 게이트의 자동 retire는 "참조 0" 판정을 요구하고, §6은 부재 추론을 sound 라벨에만
허용한다(옳은 규칙이다). 그런데 sound 참조 엣지의 공급원은 scip-typescript 하나 — self 한정이다.
외부 코드 도메인은 tree-sitter 근사층뿐이므로, 초안 자신의 규칙에 의해 **소비 시효가 외부 코드
도메인에서 격발될 수 없다**.

**실패 시나리오**: 외부 도메인 가동 수개월 후, definition-only concept이 시효 없이 무한 적체된다
— provisional_terms 3.5개월 동결의 "정확한 해독제"(§3.2)라던 메커니즘이 외부에선 처음부터 꺼져
있다. 이를 켜려면 언어당 정밀 인덱서(scip-java, scip-python 등 — 실재 여부·성숙도는 언어별 확인
필요)를 도입해야 하는데, SCIP 계열 인덱서는 각 언어의 빌드 시스템으로 **컴파일 가능한 프로젝트**를
요구한다 — 임의 외부 코퍼스에서 빌드 성립은 보장이 없고, 인덱서별 운영 부담(버전·빌드 환경·부분
실패)은 "외부 도메인 확장 시 추출기 하나를 더하는 것으로 끝난다"(§6)는 주장을 정면으로 부정한다.
그 문장은 스프레드시트 추출기에 대해서만 참이고, 정밀 코드 증거에 대해서는 언어당 부채다.

**repair**: (a) 외부 도메인의 시효 게이트를 "sound 증거 가용 시에만 활성, 아니면 시효 없음 +
적체 카운트 1급 공시"로 명시 강등하고, (b) §6 표에 "정밀층 가용성 = self(TS)만, 언어 확장은
언어당 SCIP 인덱서 + 빌드 성립 요구"를 비용 행으로 박아라. 설계 구조는 살지만 R6의 "특수 사례"
서사는 약해진다.

## F-5 (medium) — 단일 append-only JSONL + 단조 seq는 git 브랜치 워크플로와 충돌한다

§2.3 진실 = `ledger/admission.jsonl`, §5.5 되돌리기 매체 = git. 이 repo의 실제 개발은 브랜치
기반이다(지금 이 검증도 feat 브랜치에서 돈다).

**실패 시나리오**: feat 브랜치에서 reconstruct run이 seq 18232-18300을 append. 같은 기간 main의
진화 run이 seq 18232-18250을 append. 머지 시점에 진실 파일 자체가 충돌하고, 충돌 해소(수동 편집)는
§2.3이 "무효"로 규정한 손편집을 **진실 파일에 대해** 강제한다. 단조 seq도 깨진다. "커널이 유일
쓰기 경로"라는 보장은 프로세스 수준이지 브랜치 수준이 아니다.

**repair**: run별 세그먼트 파일(`ledger/segments/<run_id>.jsonl`) + 머지 시 결정론 union·reseq
투영, 또는 원장 쓰기를 main 한정으로 제약하고 브랜치 run은 proposed 상태로만. 어느 쪽이든 설계에
명시가 필요하다 — 현재 초안엔 브랜치 동시성 시나리오가 부재한다.

## F-6 (medium) — L0 사람 게이트가 1인 운영에서 자기승인으로 퇴화한다

§5.1 L0 변경 = owner 비준 + 이종 계열 독립 리뷰. 커널 v0은 신품 코드다 — 1년차에 버그픽스가
빈발한다(스키마 결함, 색인 corruption, 투영 버그). 매 픽스마다 이 중량 게이트를 통과해야 한다.

**실패 시나리오**: 스키마 버그로 전 수용이 막힌 날. 수리자 = 비준자 = 같은 한 사람. 게이트는
형식상 통과되지만 실질은 자기승인 + 절차 비용이고, 반복되면 비준이 도장으로 퇴화한다 — R2의
3중 장치가 지키려던 바로 그것이 운영 압력으로 무너진다. 또는 정직하게 지키면 커널 버그픽스
리드타임이 이종 리뷰 왕복만큼 늘어나 가용성이 죽는다. 실측 제약: owner의 이종 프론티어 좌석은
현재도 spend limit로 제약된 이력이 있다(fable-5 월 한도).

**repair**: 핫픽스 차선(즉시 적용 + 사후 이종 리뷰 의무 + 미이행 시 다음 run 블록)을 L0 게이트에
명시하고, "커널 동결" 주장을 "v1 안정화 후 동결"로 시점 조정하라. 자기승인 서사의 순도는 낮아지나
1인 운영에서 지켜질 수 있는 형태가 된다. 지켜질 수 없는 게이트가 가장 나쁜 게이트다.

## F-7 (medium) — 스프레드시트 추출기: "sound" 라벨이 거짓이 되는 입력이 흔하고, self 루프가 한 번도 연습하지 못한다

§6은 셀·수식 의존 그래프를 soundness=sound로 표기한다. 실제 스프레드시트의
`INDIRECT("Sheet"&A1&"!B2")`, `OFFSET(...)` 동적 참조는 정적 수식 파싱으로 엣지를 낼 수 없다
— 이 셀들이 낀 의존 사슬에서 정적 그래프는 엣지를 **누락**하며, 그 위의 부재 추론("이 셀은
소비자 없음")은 F-1과 같은 부재 오판을 낳는다. 또한 초안 스스로 인정하듯 스프레드시트는 self에
없는 유일 소스종이다 — 자기 루프의 "R6 대부분 통과" 보증이 정확히 이 추출기만 비켜간다.
undogfooded로 외부 도메인에 첫 출하된다.

**repair**: INDIRECT/OFFSET/동적 이름 참조가 낀 시트·사슬을 근사(approximate)로 자동 강등하는
규칙을 추출기 스펙에 명시(결정론 판정 가능 — 수식 내 해당 함수 존재 여부)하고, 6단계 외부 검증
코퍼스에 스프레드시트 포함을 done-when으로 박아라.

## F-8 (medium) — Tier-1 LLM 호출량 추정이 없고, 예산 캡 아래에서 고정점 신선도가 조용히 부패한다

§5.4 Tier-1은 증거 델타마다 부분 재귀납(LLM)을 트리거하고, §5.5 재판정 큐는 "예산 하에 배치"다.
초안 어디에도 호출량·빈도·비용 추정이 없다.

**실패 시나리오**: 활발한 개발 주간(이 repo의 실제 리듬 — 일 단위 커밋 다수). 커밋마다 Tier-1
트리거 + norm 개정발 재판정 큐 적재. 커널 예산이 캡을 걸면(걸어야 한다 — INV-LOOP-1 승격) 큐가
적체되고, stale llm_claimed verdict 비중이 단조 증가한다. 공시는 되지만("정직한 자기무지"),
운영자는 매주 커지는 발산 리포트를 받는 상태가 되고 "체계가 스스로를 파악한다"의 실질 가치가
"체계가 스스로를 모른다는 걸 안다"로 미끄러진다.

**repair**: Tier-1 트리거를 커밋 단위가 아니라 배치 윈도(run 명시 요청 시 + 주기)로 묶고,
재판정 큐에 우선순위(blocking-인접 > 공시 전용)와 적체 상한(초과 시 Tier-1 자동 강등 공시)을
설계에 명시하라. 그리고 §12 프로브에 호출량 실측 항목을 추가해 arm당 디스패치 수를 기록하라 —
지금 설계엔 이 수치의 자리 자체가 없다.

## F-9 (low) — 커널 ≤3k줄은 열거된 책임 대비 과소추정으로 보인다

L0가 소유한다고 열거된 것: 4-kind 스키마, 수용 게이트 4종, 원장+해시 색인, checker 실행기+
combinator 3종, fixedpoint Tier-0/1/2 비교기+발산 리포트 스키마, **투영(theory YAML·색인·프롬프트
payload·MCP 응답)**, budget. 현행 코드베이스에서 프롬프트 payload 투영과 MCP 응답 표면만으로도
수천 줄 규모다(프롬프트 예산 절단·demotion 순서·구간 결속이 전부 여기 산다). 발산 리포트의
결정론 하한(개념 외연 중첩률 계산 등)도 자잘하지 않다. 2-5배 초과를 예상하며, 초과 시 "1회 사람
감사 가능"이라는 무한퇴행 종결 논거(§5.1)가 정량적으로 약해진다.

**repair**: 투영 중 프롬프트 payload·MCP 응답을 L0 밖(비준 게이트는 없되 golden-projection
테스트로 봉인되는 별도 층)으로 빼고, L0는 원장·수용·checker 실행·Tier-0 비교만 남겨라. 단
"theory YAML = 진실의 투영" 보증은 L0에 남아야 하므로 경계 절단을 설계에 명시해야 한다.

## 시도했으나 초안이 견딘 공격

- **"스택이 실재하는가"**: 전 부품 실재. 유일 신규 scip-typescript도 실재하며 self=TS 한정
  채택은 방어적으로 옳다(F-4는 그 한정의 *귀결*을 공격한 것이지 채택 자체가 아니다).
- **"보류 목록이 위장 도입인가"**: Soufflé/Snorkel/SHACL/clingo 보류는 격발 조건이 붙어 있고
  실제로 도입하지 않는다 — 건전하다.
- **"이행이 비가역인가"**: 단계별 되돌리기 경로와 §12 실패 시 축소 경로(1-2단계 산출물 유효)는
  매몰 비용 관리로서 실제로 성립한다.
- **"게이트 수 폭발"**: §9의 kind×stratum 상한이 combinator 저작 비용을 유한하게 묶는다 — 현행
  스테이지 ~100 실패의 반성이 실제로 반영됐다.
- **"원장 저장 규모"**: 단일 사용자 도구에서 JSONL+git의 저장 규모 자체는 문제가 아니다(F-5는
  규모가 아니라 브랜치 동시성 공격이다).
