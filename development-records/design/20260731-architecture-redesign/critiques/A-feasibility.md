# 초안 A 적대적 검증 — 렌즈: 구현 실현성과 비용

> 검증자 노트. 2026-07-31. 대상: `drafts/draft-A.md` 전문 실독.
> 검증 방법: 초안 전문 + research 노트 대조(`theory-datalog-incremental.md`, `theory-program-analysis-substrate.md`) + repo 실측(spreadsheet-structure-observer 3,359줄 실재·수식/교차시트 참조 처리 확인, code-structure-observer 1,144줄).
> 이전 실행분 존재 공지: 이 경로에 선행 검증분이 있었다(스냅샷: scratchpad/A-feasibility.prev.md). 본 노트는 독립 저작이며 선행분의 findings(정밀 tier 캐시 키의 cross-file 의존 누락, claimed 키의 이웃 사실 누락, demand의 부트스트랩 순환)를 편입하지 않았다 — 병합은 상위 워크플로 몫.
> 종합 판정: **major_gap** — 치명 결함은 없으나, 초안의 핵심 비용 주장(커널 소형·배치 초 단위·demand 감축·롱테일 근사)이 초안 자신의 검증 계획(M0·§12)으로 검증되지 않는 구조다. 전부 수리 가능하지만 수리 전에는 실현성 판단이 미검증 가정 위에 서 있다.

## F-1 [high] 신규 코드 총량과 기간이 "커널 2~4k줄" 프레임에 가려져 있다

초안은 봉인 대상 커널만 수치화하고 나머지 신규 표면을 계상하지 않았다. 실제 신규 저작 목록: 규칙 AST 스키마+`.dl` 렌더러, shadow 계층 후보 채점기(전체 EDB 위 support/exceptions/consumption 전수), demand 큐+접지 러너+수신확인 재조정 재획득, promotion 이중평가 diff 엔진, AST→Soufflé 번역기, label model TS 재구현, 추출기 5계열의 spine 매핑+coverage 방출 개조, MCP 표면 3종, 원장 4종. 비교 기준: 현행 code-structure-observer *하나*가 1,144줄, spreadsheet observer가 3,359줄. 전체 신규 표면은 보수적으로 2~4만 줄+테스트이며, 1인 기준 M0~M6은 수개월(6개월±) 트랙이다 — 그 기간 내내 현행 시스템 유지와 병행(F-7).

**실패 시나리오**: M0 "수일" green(μ-커널+G1·G7 패리티는 실제로 수일 가능) → 실현성 입증으로 오판 → M4~M5에서 접지 러너·채점기·번역기의 실 비용이 드러나 이행 중간 좌초 → 두 시스템 영구 병존(유지 표면 2배 — 최악의 결말).

**repair**: 컴포넌트별 줄수·기간 예산표를 설계에 추가하고 M0 성공 기준에 "잔여 컴포넌트 비용 재추정"을 포함하라. "커널이 작다"와 "시스템이 작다"를 분리 서술하라. LCF 봉인 서사도 수정 필요 — 판정 무결성이 실제로 걸린 신뢰 기반(추출기 coverage 정직성, 번역기, 채점기)은 봉인 경계 밖에 있다.

## F-2 [high] coverage의 CWA 닫힘 논증이 "돌렸다"와 "전수 추출했다"를 혼동한다 — blocking 층 건전성 구멍

§2.1은 coverage 예외를 "어떤 추출기가 어떤 범위를 돌았는지는 커널 실행 기록이라 닫혀 있다"로 정당화한다. manifest가 닫는 것은 *실행 사실*이지 *추출 완전성*이 아니다. tree-sitter import 추출은 exact가 아니다: 동적 `import(expr)`, 계산된 require 경로, `export * from` 재수출 체인, 파스 ERROR 노드. 그런데 §2.3의 blocking 규칙 `no_mock_import`는 `coverage("imports","scope_src")`를 guard로 소비하고 어휘 발췌는 imports를 `soundness: exact`로 선언한다.

**실패 시나리오**: production 파일이 재수출 체인 경유로 mock 모듈에 닿거나 부분 파스로 imports 사실 누락 → 추출기는 여전히 scope 전수 coverage 방출 → 부정 guard 충족 → blocking 규칙 미발화 = **차단 층에서 거짓 green**. unknown 쌍둥이는 coverage가 *있으므로* 영원히 발화하지 않는다. 이 설계가 가장 자랑하는 장치(부재 오판의 3치화)가 추출기의 미검증 정직성 하나로 무력화된다.

**repair**: (1) coverage를 파일 단위 조건부로 강등 — 파스 클린 파일만 계상, ERROR 노드 파일은 자동 제외되어 unknown으로 흐르게. (2) soundness 라벨을 coverage 방출 자격에 결속 — may_miss 추출기는 exact coverage를 방출할 수 없다는 커널 lint. (3) M0 변이 flip을 규칙만이 아니라 **추출기별**로 확장(사실 누락 주입 → unknown 전환 확인).

## F-3 [high] 재귀+why-provenance의 규모가 미계산이고, M0 스파이크는 이를 건드리지 않는다

§2.1은 도달성·전이 폐포를 "이 단편의 본령"으로 선언하고 모든 도출 원자에 provenance를 기록한다. TC의 원자 수는 엣지 수가 아니라 **쌍 수**로 자란다: 자기 코퍼스만 해도 16.2만 줄이면 SCIP 참조 엣지 10⁵~10⁶대가 현실적이고, unit 수천 개 위 도달성은 10⁶~10⁷ 도출 원자+원자당 증명 기록이 된다. research 노트의 "수백만 튜플 초 단위"는 **Soufflé(컴파일된 C++)의 수치**인데 초안 §7은 이를 자작 TS 평가기의 배치 낙관("배치가 이미 초 단위일 가능성")으로 이월했다. JS 힙의 naive 조인+원자당 provenance 객체는 다른 비용 등급이다. 결정적으로 **M0 패리티 대상 G1·G7은 비재귀 조인 규칙**이라, 최대 성능 리스크(재귀 at 규모)는 M3 replay까지 한 번도 실행되지 않는다.

**실패 시나리오**: M0~M2 green → M3에서 의존 도달성 규칙이 든 이론으로 자기 코퍼스 replay → 고정점이 분 단위 초과 또는 힙 폭발 → 커널에 인덱싱·magic sets·재귀 제한 소급 증축 → "사람 1회 감사 가능한 소형 커널" 봉인 전제와 정면 충돌.

**repair**: M0 성공 기준에 (a) 자기 코퍼스 실 엣지 볼륨 실측, (b) 재귀 규칙 1개(도달성) 포함, (c) 배치 시간·힙 상한의 수치 기준(INV-BENCH-1 규율) 추가. TC가 규모 벽에 닿으면 도달성을 커널 재귀가 아니라 추출기 사전계산 checked 사실로 강등하는 퇴로를 명기하라.

## F-4 [high] 비-TS 코퍼스에서 admission의 consumption 축이 무너진다 — M5가 첫 충돌 지점

research 노트 스스로 "정밀 참조 엣지와 언어당 툴체인 회피는 양립하지 않는다"고 결론냈다. 초안의 처리는 "롱테일은 tree-sitter 근사 + may_miss"인데, tree-sitter는 name resolution을 안 하므로 참조 엣지가 *근사*로라도 나오려면 언어당 쿼리+휴리스틱 해석기를 신규 저작해야 한다(14언어 부채, 미계상). SCIP 정밀 tier는 언어당 실 빌드 환경을 요구한다 — "사람 관여 최소로 임의 구현물에서 reconstruct"라는 미션 전제와 "먼저 그 repo의 빌드를 세팅하라"는 운영 현실이 충돌한다. 관념적 우려가 아닌 이유: **admission의 consumption 축(§3 단계 2)과 demand 정책 예시(fan_in)가 둘 다 references 위에 서 있다.**

**실패 시나리오**: M5 reconstruct-lite를 비자기 코퍼스(예: Python repo)에 실행 → scip-python 빌드 환경 부재로 references 결손 → 전 후보 inbound_references=0 → consumption 축이 전 후보를 `rejected_no_consumption`으로 기각(§2.3의 처분 예가 정확히 이 판정 모양이다) 또는 coverage 정직 강등 시 전 판정 unknown → 이론 귀납이 빈손. 초안의 자기 예시(timeout_seed_assembly 기각)가 비-TS 코퍼스에서 **전 후보 오판**으로 재현된다.

**repair**: consumption 축을 `coverage(references, scope)` 존재에 조건부로 — coverage 부재 시 consumption은 채점 제외(unknown), 기각 사유 사용 불가라는 admission 수정. M5 대상을 "SCIP 가용 언어"로 사전 제약하든지, references-없는 admission 경로를 설계하고 판별력 저하를 공시하라.

## F-5 [medium] Soufflé 차등 오라클이 정확히 가장 위험한 자작 부분을 못 덮는다

DDC-lite가 대조하는 것은 순수 Datalog 고정점 — 자작 커널에서 *가장 덜* 틀릴 부분이다. 커널 고유 확장(unknown 쌍둥이 자동 생성, taint 전파, 채널 방출 조건, 집계·산술 모서리 의미론)은 Soufflé에 대응물이 없어 오라클 범위 밖이고, 대조용 AST→Soufflé 번역기는 그 자체가 미검증 신뢰 컴포넌트다(번역기가 정규화하며 버그를 양쪽에 복제하면 오라클 침묵 통과). Soufflé와의 의미론 차이(빈 그룹 집계, 계층화 granularity)는 거짓 diff 소음을 만들어 오라클 규율을 침식한다.

**실패 시나리오**: 쌍둥이 생성기의 guard 매칭 버그로 특정 규칙 클래스에서 쌍둥이 미생성 → 부재 오판이 조용히 부활 → 오라클은 쌍둥이를 아예 모르므로 green → F-2와 결합해 핵심 차별점이 이중 무검증.

**repair**: 쌍둥이·taint를 커널 내부 특수 장치가 아니라 **번역 전 desugaring으로 보통 Datalog 규칙에 전개**해 오라클 범위 안으로 넣어라(쌍둥이는 이미 보통 규칙 형태다 — §2.3 렌더가 증거). 번역기는 1:1 구문 사상으로 최소화하고 오라클 대상 단편을 명시 선언하라.

## F-6 [medium] LLM 호출량·지연이 어디에도 계산되지 않았고, claimed 캐시 키가 리팩터에 취약하다

demand 감축 주장은 저자도 §13.3에서 "계산이 아니라 설계"라 인정했다 — 그런데 §12 반증 실험 3종 어디에도 호출량 추정 실험이 없다. 이는 라이브 LLM 없이 결정론적으로 계산 가능한데(자기 코퍼스 EDB에 demand 규칙을 돌려 큐 크기를 세면 된다) 빠져 있다. 추가로 claimed 키에 unit sha가 접혀 있어 시그니처 불변의 포매팅·리네임 리팩터도 닿은 전 unit의 접지를 무효화한다.

**실패 시나리오**: 100파일 리네임 리팩터 → 접지 캐시 전멸 → 재접지 큐 = 변경 unit × claimed 술어 × 다중 렌즈, 수신확인 왕복 포함 → 예산 상한에 눌려 대부분 unknown → review 산출물이 "unknown 목록"으로 퇴화. 현행 병목(소형 fixture 25~26콜·12~20분)보다 나쁜 체감이 나올 수 있는데 아무도 계산해 보지 않았다.

**repair**: §12에 실험 4 추가 — 자기 코퍼스에 demand 정책을 돌려 큐 크기·왕복·지연을 수치화(LLM 지출 0). 캐시 키의 unit sha를 정규화 본문 sha(공백·주석 제거)로 바꿔 무의미 무효화를 줄이는 것을 검토.

## F-7 [medium] 이행기 이중 유지보수가 1인 체제에서 미계상이다

M2~M6 동안 불변식·가드의 모든 변경이 두 곳(현행 G-가드 + 이론 규칙)에 착지해야 하고, 현행 제품 유지보수(인증 좌석·resume·배달 재조정 — 초안 스스로 "실전 경화" 자산으로 인정)도 계속된다. 초안은 병존 자체는 인정(§10 손실 1, §11)했으나 이중 기입 기간의 규율 — 변경이 양쪽에 동기 착지하는 비용과 드리프트 탐지 — 이 없다.

**실패 시나리오**: M3 시점 현행 시스템에 신규 불변식 추가(실제 빈도: 최근 한 달에도 INV-SHARD-1 신설) → 이론 쪽 미러 누락 → M3 replay diff가 "이론이 못 잡은 finding"을 보고 → 이론 품질 문제인지 미러 누락인지 분리 불가 → replay 신호 오염.

**repair**: 이행기 규칙 명시 — 불변식 동결 창을 선언하거나, 신규 불변식은 이론-우선 저작 후 G-가드로 역투영하는 단방향 규율을 M2부터 강제.

## F-8 [low] label model TS 재구현은 통계 전제가 깨진 자리의 과잉 부품이다

Snorkel류 label model의 전제는 다수 항목 + (조건부) 독립 labeling function이다. 이 설계의 투입은 unit당 렌즈 2~5표이고, 초안 스스로 렌즈 겹침을 품질 메커니즘으로 인용한다(§4) — 상관이 *설계 의도*다. 상관된 소수 투표에서 label model은 가중 다수결로 퇴화하고, 참조 구현 패리티 없는 통계 모델의 TS 재구현·검증 비용만 남는다.

**실패 시나리오**: 렌즈 3표(2 상관) 위에서 상관 쌍에 이중 가중 → 신뢰도 추정이 단순 다수결보다 나쁨 → 그 수치가 claimed 메타데이터로 원장에 박제되어 거짓 정밀 공급.

**repair**: v1은 결정론 일치 카운트(합의 n/m + 렌즈 id)로 시작, label model은 접지 원장이 항목 수를 충분히 쌓은 뒤(문턱 명시) 별도 결정으로 구매.

## F-9 [low] "TS-native 성숙 Datalog 부재 실사"는 원 노트의 "확인필요"를 확정으로 승격했다

research 노트 원문(theory-datalog-incremental.md:86)은 "TS-native 성숙 Datalog는 사실상 없다(실험적 구현들 뿐 — **확인필요**)"다. 초안 §8은 이를 "(research 실사)"로 인용한다. 결론 자체는 아마 옳다(나도 반박할 성숙 후보를 제시하지 못한다 — DataScript는 쿼리 엔진이지 계층화 규칙 평가기가 아니다). 그러나 커널 자작이라는 최대 비용 결정의 근거 문장이 미확인 표기를 잃은 채 승격된 것은 초안의 자기 규율(확신 없는 것은 확신 없다고 표기) 위반이다.

**repair**: 실사를 실제로 1회 수행(후보 3~5개 나열·기각 사유)해 노트에 박제하거나, 인용을 "확인필요 유지"로 정정.

## 판정 요약

날조된 스택은 없다 — 부품은 전부 실재하고, R5 캐시 단위도 정의됐다. 문제는 **비용 주장의 검증 구조**다: 초안의 자기 검증 계획(M0·§12)이 (a) 신규 코드 총량, (b) 재귀 규모, (c) 비-TS 코퍼스, (d) 호출량 — 실현성이 실제로 걸린 네 축을 하나도 실행하지 않는다. M0가 설계대로 green이어도 실현성은 입증되지 않는다. 전 findings에 수리가 존재하므로 fatal은 아니나, 수리 전 상태로는 major_gap이다.
