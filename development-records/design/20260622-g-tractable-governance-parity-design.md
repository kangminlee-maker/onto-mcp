## 1. Why (the recurring gap)

Across M3c (#106) and M4b (#107), codex/onto repeatedly flagged "declared in the registry but not loader-enforced / not registry-declared": `input_authority_refs` not resolution-checked, `validation_obligations` declarative-only, prompt-projection fields added without a registry home. G closes the **prompt-surface + registry-shape drift** class (G(b)/G(c)) and unblocks the obligation-coverage class (loader extension), without the heavy G(a) dynamic proof.

## 2. Confirmed current state

- **Loader drops obligations**: `parseValidatorRecord` (contract-registry.ts:703-709) keeps only `validator_id/gate_ids/validator_version/input_authority_refs/output_ref`. `validation_obligations` (301 lines / 48 validators) and `conditional_validation_obligations` (3) are parsed away — codex H-B. A coverage gate would run on empty data; first preserve the data.
- **Prompt-projection contract has no registry home**: `competencyQuestionAssessmentProjectionContract()` (run.ts:800) returns ~14 top-level keys + budget constants; only its version+sha rotate the reuse hash; no registry declares the field set (the M2/M3c "new field undeclared" class).
- **Final-output append sections diverge across 3 representations** (codex M-9): the prompt policy `deterministic_runtime_append_sections` (run.ts:4447) uses 5 **underscore** ids (`seed_answerability, claim_projection, artifact_truth, provenance_footer, provenance_bindings`); `finalOutputProvenanceSectionBindings` (run.ts:10471) uses 5 **hyphen** sections (`seed-answerability, artifact-truth, claim-projection, runtime-artifact-truth-footer, runtime-provenance-bindings`) with full metadata; the M4a `unresolved_revision_proposals` disclosure section is in NEITHER list. No registry owns the canonical section set.

## 3. Design

### 3.1 Part 1 — Loader extension (preserve obligations; no gate)
- `ReconstructValidatorRecord` (contract-registry.ts type) += `validation_obligations: string[]` (flat string ids — correct) and `conditional_validation_obligations: ConditionalValidationObligation[]`.
- **xval #12/#18/#22/#26/#29/#30 — the conditional shape is STRUCTURED, not string[]**: inspect registry lines 2245-2249 / 2304-2313 / 2701-2705. Type `ConditionalValidationObligation = { obligation_id: string; activation_condition: string; input_authority_refs: string[] }` (default `input_authority_refs` to `[]`). Add a `parseConditionalValidationObligation` helper. NOTE a SEPARATE `conditional_input_authority_refs` field (`{artifact_ref, activation_condition/required_when, consumed_for}`, registry ~2283-2292) is ALSO dropped by `parseValidatorRecord` — it is a different concept (input gating, not obligation gating); **scope it OUT of this PR explicitly** (do not parse it here; note for a future loader-completeness pass).
- `parseValidatorRecord` parses both new fields (optional; default `[]`). No coverage gate — that is G(a), deferred.
- **xval #1 (HIGH) — DO NOT rotate the governing-snapshot / reuse hash**: `buildReconstructRunGoverningSnapshot` embeds the WHOLE `args.contractRegistry.validator_records` in the `validator_records` snapshot family (governing-snapshot.ts:575-581) and `snapshotFamily` hashes it via `sha256Text(stableJson(value))` (:445); that sha flows into `authoredArtifactReuseMatch.governing_snapshot_sha256` (run.ts:1262). Adding obligation fields to every parsed record would rotate the snapshot family sha → rotate the reuse hash → force re-author of all prior artifacts + break golden snapshot fixtures. **FIX: project the validator records to the existing 5-field shape BEFORE embedding in the snapshot family** (keep ONLY `validator_id`/`gate_ids`/`validator_version`/`input_authority_refs`/`output_ref`), mirroring the `validator_versions` projection at governing-snapshot.ts:546-553. So the loader exposes obligations but the governing snapshot's `validator_records` family stays byte-identical → zero hash rotation, zero reuse/fixture regression. (Verify with governing-snapshot.test.ts + the reuse-provenance tests.)
- **onto issue-001 — make the projection a named ALLOW-LIST helper, not an inline strip-the-2-known**: implement the fix as a named `projectValidatorRecordSnapshotFields(validator)` helper in governing-snapshot.ts that returns exactly the 5 allow-listed fields, and call it in the `validator_records` family `value` map. An allow-list (return only the 5) is durable: any FUTURE parsed validator-record field is excluded by default (it would have to be consciously added to the helper to enter the snapshot), so the no-rotation guarantee holds for the whole field class, not just `validation_obligations`/`conditional_validation_obligations`. A strip-list (delete the 2 known) would silently re-leak the next added field. (onto evolution finding-003 + coverage finding-001: the design's no-rotation property must be a structural boundary, not a current-two-fields regression check.)
- Verify with the real loader (`loadReconstructContractRegistry`) test: a known validator record exposes its `validation_obligations` (non-empty) + structured conditional after load. (Per memory: registry edits checked with the real loader, not grep.)

### 3.2 Part 2 — G(b) field-parity (`prompt_projection_contracts` registry node + guard)
- Registry node `prompt_projection_contracts.competency_question_assessment` declaring the EXACT expected surface, structured to avoid the codex M-8 "ad-hoc Object.keys mixing payload+nested-policy" trap:
  - `payload_fields`: the top-level keys of `competencyQuestionAssessmentProjectionContract()` (projection_kind, projection_contract_version, semantic_authority, prompt_char_limit, question_projection, evidence_projection, source_evidence_projection, source_evidence_excerpt_char_limit, source_evidence_reserve_derivation, validation_projection, claim_realization_projection, runtime_derivations, batching_policy, fail_loud_policy).
  - `policy_fields`: the keys of the nested `batching_policy` (mode, order, build_budget_reserve_chars, single_question_overflow).
  - `budget_fields`: the named budget constants the contract embeds (prompt_char_limit=50000, source_evidence_excerpt_char_limit=4000, build_budget_reserve_chars=1000; + candidate_limit=50 if declared).
  - **xval #33 — `budget_fields` = exactly the 3 budgets the contract OUTPUT embeds** (`prompt_char_limit`=50000, `source_evidence_excerpt_char_limit`=4000, `batching_policy.build_budget_reserve_chars`=1000). DROP `candidate_limit` (the EVIDENCE_CANDIDATE_LIMIT=50 is an internal runaway-guard cap NOT in the contract output; the parity guard cannot see it).
- **xval #17/#19/#21/#27/#31 (consensus) — EXTRACT a module; do NOT export from run.ts**: scripts importing the 13k-line run.ts is off-pattern (and `check-import-boundary` only scans `src/**`, so it wouldn't even catch it). Move `competencyQuestionAssessmentProjectionContract()` + its budget constants into a small side-effect-free module `src/core-runtime/reconstruct/competency-projection-contract.ts` (sibling to `seed-claim-projections.ts`); `run.ts` imports from it; the guard imports from it. Single source of truth, guard stays cheap.
- New guard `scripts/check-prompt-projection-parity.ts`: imports the registry node + the extracted contract module; asserts the declared `payload_fields`/`policy_fields` sets EXACTLY equal the runtime contract's top-level / `batching_policy` keys (exact-set, not subset), and the declared budgets equal the runtime constants. Fail (process.exit(1)) on add/drop/changed-value.
- **onto issue-001 (finding-002) — the guard must also enforce that `run.ts` CONSUMES the extracted module (SSOT consumption, not just registry↔module parity)**: a registry-vs-module parity check passes even if `run.ts` still defines its own stale `competencyQuestionAssessmentProjectionContract` or duplicate budget constants — the prompt-surface drift class would only be half-closed (CI certifying parity against the wrong authority). The extraction itself removes the local definition (one definition exists), but nothing structurally PREVENTS a future re-duplication. So the guard additionally reads `src/core-runtime/reconstruct/run.ts` source text and asserts (i) it imports `competencyQuestionAssessmentProjectionContract` + the budget constants from `./competency-projection-contract`, and (ii) it contains NO local `function competencyQuestionAssessmentProjectionContract(` and no local redeclaration of the moved budget constants. (`check-import-boundary` checks import direction, not symbol ownership, so it cannot catch this — a source-text assertion in the parity guard is the right tool, mirroring `check-supported-models.ts`.)
- **xval #28/#32 — guard registration**: add to `check-invariant-drift.ts` `GUARDS` (entry shape `{guard, invariants, command}`). Decide the INV id: either introduce `INV-REGISTRY-PARITY-1` in INVARIANTS.md + invariants.yml (an INVARIANT-CHANGE-marked edit — extra scope) OR map to an existing invariant; the guard MUST `process.exit(1)` on mismatch (mirror `check-supported-models.ts` shape) so the aggregator flags it.

### 3.3 Part 3 — G(c) append-sections registry model — **DEFERRED to a separate follow-up PR**

Split out after cross-validation (3 lenses recommended it). NOT in this PR. The follow-up PR's spec, with the cross-validation findings already resolved, is preserved here:

- **The runtime emits 8 final-output sections, not 6** (xval #0 HIGH): the 5 provenance-binding sections (`finalOutputProvenanceSectionBindings`, run.ts:10471) PLUS three conditional appends at the emit site (run.ts ~13280-13446): `## Source Projection Truncation` (appendFinalOutputDocumentProjectionTruncationSection ~10030), `## Workbook Inventory Projection Truncation` (~10065), `## Unresolved Revision Proposals` (appendFinalOutputUnresolvedRevisionSection ~9981). The registry list must enumerate ALL 8 (the two truncation siblings have `append_owner=runtime`, activation-gated, `provenance_binding_required=false`), and the guard must assert coverage of EVERY `appendFinalOutput*Section` call — not just the bindings array — or it is foolable by a 9th truncation-style section.
- **"underscore→hyphen" is 2 SEMANTIC renames, not punctuation** (xval #10/#13): explicit alias table — `seed_answerability→seed-answerability`, `claim_projection→claim-projection`, `artifact_truth→artifact-truth`, `provenance_footer→**runtime-artifact-truth-footer**`, `provenance_bindings→**runtime-provenance-bindings**`.
- **Resolve Q1 = parity-guard, do NOT derive** (xval #7/#14 HIGH): keep BOTH runtime lists textually UNCHANGED; the registry declares canonical `{section_id, prompt_policy_id, heading, append_owner, activation_predicate, provenance_binding_required}` rows; the guard asserts (i) the prompt-policy list equals the declared `prompt_policy_id`s (via the alias map) and (ii) the binding section_ids+headings equal the declared ones. Deriving would either change the prompt surface (breaks run.test.ts:4204-4211, xval #2/#4/#5/#11/#16) or make the guard vacuous (compare registry to itself).
- **The hyphen section_ids are load-bearing `required_fragments`** (xval #6 HIGH, run.ts:10606-10611) — do NOT rename them; the registry adopts those exact strings as canonical.
- **Guard on BOTH section_id AND heading** (xval #8 HIGH): the heading set is the runtime load-bearing identity (`validateFinalOutputProvenance`, post-seed-validation.ts ~2121-2141) — heading is the primary parity key.
- **`unresolved-revision-proposals` has NO `section_id` in code** (xval #3/#15/#23 HIGH): it is a conditional markdown heading only. Either give the M4a emitter a real `section_id` constant and assert equality, or classify it in the registry as `append_owner=runtime_markdown`, `provenance_binding_required=false`, `activation_predicate=disclosed_proposals_nonempty` and have the guard assert the runtime FUNCTION emits the `## Unresolved Revision Proposals` heading literal (source-text presence) — otherwise the "present" check is vacuous.

## 4. Concept economy (THIS PR = loader + G(b))
- Loader: +2 fields on an existing type + 1 conditional-obligation type + the snapshot PROJECTION fix as a named `projectValidatorRecordSnapshotFields` allow-list helper before the snapshot family. No new concept (obligations already in YAML; the helper is a local projection sibling to the existing `validator_versions` inline projection, promoted to a named function so the allow-list is explicit and testable).
- G(b): 1 registry node + 1 extracted projection-contract module + 1 guard script. Single source of truth (the extracted contract fn).
- 1 new guard script registered in the existing `check-invariant-drift` aggregator (no new aggregator).
- **G(c) split to its own PR; G(a) deferred** (no `asserted_obligation_ids`, no coverage gate).

## 5. Success criteria (THIS PR)
- The loader preserves `validation_obligations` (string[]) + `conditional_validation_obligations` (structured) on every parsed validator record (proven by the real loader test) — and the governing-snapshot `validator_records` family sha is UNCHANGED (no reuse-hash rotation; governing-snapshot.test + reuse-provenance tests pass).
- The projection boundary is enforced as a structural invariant (named `projectValidatorRecordSnapshotFields` allow-list helper + exact key-set test + future-extra-field test), not just a sha-vs-main regression — so a later parsed validator-record field cannot silently rotate the snapshot/reuse hash (onto issue-001).
- The prompt-projection field set is registry-declared; adding/dropping a field in `competencyQuestionAssessmentProjectionContract()` (or a budget) without updating the registry fails CI (exact-set), and vice versa.
- The G(b) guard enforces SSOT *consumption*: `run.ts` imports the contract fn + budgets from the extracted module and holds no duplicate definition; a re-duplication fails CI (onto issue-001 / finding-002).
- Zero runtime regression: full vitest + guards green (baseline after M4b = full vitest 1747).
- G(c) and G(a) explicitly out of scope (documented; G(c) spec preserved in §3.3).

## 6. Test plan (THIS PR)
- loader: a test asserts a known validator record exposes its `validation_obligations` (non-empty) + structured conditional after `loadReconstructContractRegistry`; + a governing-snapshot test proving the `validator_records` family sha is unchanged vs main (the projection works).
- **loader projection boundary (onto issue-001 / finding-001 + finding-003)** — two structural assertions beyond the sha-vs-main regression:
  - **exact key-set coverage**: build the governing snapshot and assert EVERY record projected into the `validator_records` family has exactly `{validator_id, gate_ids, validator_version, input_authority_refs, output_ref}` and no `validation_obligations`/`conditional_validation_obligations`. (Guards the per-record domain, not just the aggregate hash.)
  - **future-extra-field boundary**: take a loaded validator record, add an extra non-snapshot field (e.g. a synthetic key beyond the two obligation fields), rebuild the snapshot, and assert the `validator_records` family `sha256` + `selected_ids` are identical to the 5-field projection. Proves `projectValidatorRecordSnapshotFields` is an allow-list (future fields excluded by default), so the no-rotation property is durable, not specific to today's two fields.
- G(b): guard passes on the current matched state; a negative/self-test proves it fails when a payload/policy field is added/dropped or a budget changes.
- **G(b) SSOT consumption (onto issue-001 / finding-002)**: the guard asserts `run.ts` imports the contract fn + budget constants from `./competency-projection-contract` and defines no local copy; a self/negative check proves the guard fails if `run.ts` reintroduces a local `competencyQuestionAssessmentProjectionContract` or duplicate budget constant.
