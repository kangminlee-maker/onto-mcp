# Review Synthesis Map-Reduce Design

> Status: implemented; live verification active
> Date: 2026-06-06
> Scope: review pipeline `synthesize` / `final-output` boundary optimization
> Current work order: `development-records/plans/20260607-review-pipeline-remaining-work-order.md`

## Goal

Improve review pipeline speed and stability without reducing semantic quality.

The current `synthesize` stage was originally responsible for reading all lens
outputs, recognizing same-issue expressions, classifying consensus and
disagreement, and writing the final review result. That role is now too broad.
The pipeline has already introduced upstream artifacts that own most of this
semantic structure:

- `finding-relation-graph.yaml` owns same-root, shared-cause, and dependency
  candidate relations.
- `issue-ledger.yaml` owns root-cause issue clustering and issue-level truth.
- `issue-stance-matrix.yaml` owns per-lens issue stance.
- `deliberation-plan.yaml` owns which material conflicts require deliberation.
- `deliberation-resolution.yaml` owns contested issue resolution.
- `problem-framing.yaml` owns materiality framing, timing, closure, and domain
  axes classification.

Therefore downstream synthesis should not reopen raw lens outputs to rediscover
issue identity or consensus. It should explain already-authorized issue truth at
high quality, then let runtime compose and validate the final artifacts.

## Design Summary

Replace the single broad `synthesize` step with issue-scoped synthesis work:

```text
issue artifacts
  -> runtime synthesis work-item projection
  -> parallel LLM issue synthesis
  -> runtime synthesis ledger merge and validation
  -> optional narrow global consistency pass
  -> runtime-rendered synthesis.md, final-output.md, review-record.yaml
```

This is a Map-Reduce structure:

- Map: one bounded LLM unit per material issue.
- Reduce: runtime merges validated responses into `synthesis-ledger.yaml`.
- Optional global pass: a small LLM pass reads only the ledger and improves
  overall ordering/narrative consistency without creating new claims.

## Concept Changes

| Concept | New seat | Reason |
|---|---|---|
| `synthesis-work-items.yaml` | runtime | Deterministic projection of material issues into bounded LLM work items. |
| `synthesis/responses/{issue_id}.yaml` | LLM semantic payload through structured submit | Issue-level explanation, not artifact authority over ids/severity/refs. |
| `synthesis-ledger.yaml` | runtime | Canonical synthesis truth after validation and merge. |
| `synthesis.md` | runtime projection | Human/audit view rendered from `synthesis-ledger.yaml`, not LLM-authored truth. |
| `final-output.md` | runtime projection | Principal-facing view rendered from ledger and classification summary. |

No backward compatibility aliases or fallback formats should be introduced. If
an artifact is malformed or absent on the active path, fail loud.

## Authority Boundary

### Runtime Owns

- work item ids and paths
- issue ids, finding ids, evidence refs
- material issue coverage
- severity and materiality status
- problem-framing values
- deliberation status and resolution refs
- response serialization
- merge ordering
- final markdown rendering
- ReviewRecord refs
- validation failures

### LLM Owns

- issue-level conclusion prose
- materiality explanation
- root-cause explanation
- causal-path explanation
- action explanation
- unresolved-disagreement explanation
- compact boundary-note prose
- optional global narrative consistency

The LLM may not change issue identity, severity, materiality, closure class,
domain axes, stance state, or evidence refs.

## Artifact Flow

### 1. `synthesis-work-items.yaml`

Generated by runtime after `problem-framing.yaml` is valid.

Each material issue produces one work item. Low/info findings are not sent to
LLM synthesis by default; they are preserved as compact non-material rows in the
runtime ledger.

Each work item contains:

- `work_item_id`
- `issue_id`
- `severity`
- `issue_statement`
- `affected_purpose`
- `failure_condition`
- `impact`
- `root_hypothesis`
- `causal_path_summary`
- `related_surface_findings`
- `stance_summary`
- `deliberation_resolution`
- `problem_framing`
- `action_candidate_projection`
- `boundary_note_candidates`
- `allowed_evidence_refs`
- optional bounded evidence excerpts when the upstream artifacts cannot carry
  enough context safely

Default read authority for each issue synthesis worker is the work item plus the
explicit allowed evidence refs. Raw Round 1 lens outputs and issue-scoped
deliberation responses are not default reads.

### 2. `synthesis/responses/{issue_id}.yaml`

Produced by an LLM structured-output path.

Required payload shape:

```yaml
issue_id: issue-001
conclusion: string
materiality_explanation: string
root_cause_explanation: string
causal_path_explanation: string
action_explanation: string
unresolved_disagreement_note: string | null
boundary_notes:
  - string
source_refs_used:
  - string
```

Runtime fills or validates envelope fields such as `schema_version`,
`session_id`, `created_at`, `work_item_id`, output path, and source work-item
ref.

### 3. `synthesis-ledger.yaml`

Merged by runtime from validated issue responses and non-material rows.

It contains:

- participation and run status
- material issue synthesis entries
- non-material finding summaries
- shared-cause/dependency ordering projection
- unresolved disagreement projection
- final action ordering
- boundary notes
- synthesis coverage validation summary

This artifact becomes the synthesis truth. `ReviewRecord.synthesis_result_ref`
should point to this artifact after implementation.

### 4. Optional `synthesis-global.yaml`

Triggered only when a global view is genuinely useful:

- at least two material issues
- issue dependency or shared-cause relation exists
- unresolved disagreement exists
- action ordering is not obvious from runtime projection

The global pass reads only `synthesis-ledger.yaml`. It may improve the compact
overall verdict, ordering rationale, and narrative coherence. It may not add
findings, change severity, change closure, change issue grouping, or introduce
new evidence.

If the global pass fails, the runtime can either fail loud or render from the
validated ledger. The default should be fail loud until product behavior is
explicitly defined.

### 5. `synthesis.md` and `final-output.md`

Both are runtime-rendered views.

`synthesis.md` keeps the internal review/audit heading surface.
`final-output.md` presents the principal-facing result.

Neither file is the authority for issue identity, severity, materiality,
problem framing, or evidence refs.

## Validation Gates

Runtime must reject:

- missing material issue synthesis response
- duplicate issue synthesis response
- response for unknown issue id
- unknown finding ref or evidence ref
- severity/materiality/problem-framing drift
- unresolved deliberation represented as resolved
- boundary notes above configured count/length limit
- source refs not included in allowed evidence refs
- final action candidate that is not derived from issue/problem-framing truth
- non-material finding omission from the ledger

The validation should write a structured halted execution result when the active
review path cannot continue.

## Expected Speed Effect

The current final synthesize stage is serial. With this design, material issue
synthesis is parallel.

Approximate shape:

```text
current:   one broad synthesize LLM call
new:       max(issue synthesis calls) + runtime merge + optional short global pass
```

For reviews with multiple material issues, latency should approach the slowest
single issue synthesis rather than the combined reasoning load of all issues.
For reviews with no material issues, the LLM synthesis stage can be skipped and
the final output can be rendered from runtime projections.

## Expected Quality Effect

Quality should be preserved or improved because each LLM unit receives a
smaller, issue-centered context and can spend reasoning effort on:

- why this issue is material
- what the root cause is
- how the causal chain supports the issue
- what dependency or shared-cause relation affects resolution
- what action is actually required

The design avoids lowering effort as the primary speed lever. Actor settings
remain controlled by `.onto/settings.json`; issue synthesis workers initially
reuse the existing `synthesize` actor settings unless a later settings design
adds a separate full actor config.

## Completion Criteria

The design is implemented when:

- broad single `synthesize` no longer reads all lens outputs by default
- every material issue has exactly one validated issue synthesis entry
- non-material findings remain preserved in compact ledger rows
- `final-output.md` is runtime-rendered from validated synthesis truth
- `ReviewRecord` points at the synthesis truth artifact
- semantic quality gate verifies material issue recall, non-material
  preservation, causal/dependency preservation, actionability, and grounding
- E2E and benchmark runs show packet/output reduction without semantic quality
  regression
