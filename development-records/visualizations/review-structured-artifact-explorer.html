LLM Chain Gates

The relation-graph to problem-framing span is not one unbroken free-form LLM chain. Each unit receives a runtime-built projection, submits only bounded semantic rows, and hands a validated artifact to the next unit.

Stage Runtime Input Boundary LLM-Owned Payload Runtime Gate After Submit
finding-relation-graph finding-relation input projection from finding-ledger causal paths. Accepted relation rows and rationale only. Known finding IDs, relation enum, shared-cause shape, runtime relation IDs, singleton completion.
issue-ledger Validated finding-ledger, relation graph, review-target profile, dependency context. Root-cause issue clusters and issue statements. No invented findings, coverage assignment, relation refs for multi-finding issues, dependency projection.
stance-responses / issue-stance-matrix One fresh issue-stance projection per lens; bounded supplemental ref only if needed. Lens stance rows, root hypothesis position, severity position, rationale. All issue x lens coverage, stance enums, missing issue validation, runtime matrix merge without semantic rewrite.
deliberation-plan Compact projection from issue-ledger, stance matrix, and relation graph. Material conflict selection, participant choice, resolution question, skip rationale. Every issue planned or skipped once, participants match stance refs, material-severity candidate check.
deliberation/responses Issue-scoped participant packet with source stance and peer positions. Updated stance, disagreement response, accepted root hypothesis, evidence refs. Allowed evidence refs, runtime source stance backlink, unavailable completion on worker failure.
deliberation-resolution Deliberation plan plus participant responses. Final issue status, final root cause, final claim, remaining disagreement. One resolution row per issue, missing issue validation, markdown projection from YAML truth.
problem-framing Projection from issue-ledger, stance matrix, plan, resolution, target profile, and domain axis catalog. Classification rows only. Runtime fills context and related finding IDs; common spine enum validation; domain axis validation.

Lens Sidecar Findings

round1/logic.findings.yaml
LLM + submit tool schema_version: 1 machine source

Each lens submits structured findings. For material severity hints, causal and materiality fields are required; for low/info they must be null.

lens_idlogicRuntime checks path and expected lens ID.
candidate_idlogic-candidate-001Lens-local candidate anchor.
severity_hinthighEnum: blocker, high, medium, low, info.
materiality_basis{ affected_purpose, failure_condition, impact, evidence_refs }Required for blocker/high/medium.
causal_path{ root_cause_candidate, steps[] }Required for material severity candidates.
validation{ unaddressable_candidates: [] }Runtime-visible missing-evidence surface.
unresolved_beyond_evidencenull | "needs package install smoke"Records where root-cause exploration stops at the evidence boundary.
domain_constraints_used[] | [{ source_doc, version, anchor }]Empty means no domain rule was actually used by this lens.
  • If the next causal step requires unavailable context, the lens must not invent it; it records the boundary under unresolved_beyond_evidence or marks the finding as needing upstream evidence.
  • If no evidence-backed material root can be stated, the finding should remain low or info with materiality_basis: null and causal_path: null.
